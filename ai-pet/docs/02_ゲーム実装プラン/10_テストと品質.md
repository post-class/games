# 10. テストと品質

## 1. テストの層

| 層 | ツール | 対象 | 実行タイミング |
|---|---|---|---|
| 単体 | Vitest | 純関数（ユーティリティAIのスコア、記憶検索、RNG、プロトコルzod） | 毎コミット |
| シミュレーション | Vitest（長時間） | 島を数千tick回して不変条件を検証 | 毎コミット（短）／手動（長） |
| プロトコル | Vitest | 差分生成と適用の往復一致 | 毎コミット |
| LLM | Vitest＋モック | プロンプト組み立て・出力検証・フォールバック | 毎コミット |
| E2E | Playwright | 2ブラウザ同時接続、会話、再接続 | 手動＋リリース前 |
| 見た目 | Playwright スクリーンショット | アセットのコンタクトシート、UI崩れ | アセット追加時 |

## 2. 決定論シミュレーションテスト（最重要）

`Math.random()` を禁止し、`shared/rng.ts` のseed付きPRNGのみを使うため、
**同じseedなら何度回しても同じ結果**になります。これを土台に不変条件を検証します。

```ts
// tests/sim/invariants.spec.ts
test('7島日回しても島が破綻しない', () => {
  const sim = createSim({ seed: 'test-1', critters: 100 });
  const TICKS = TICKS_PER_ISLAND_DAY * 7;
  for (let i = 0; i < TICKS; i++) sim.step();

  expect(sim.critters.length).toBeGreaterThan(40);      // 絶滅しない
  expect(sim.critters.length).toBeLessThanOrEqual(120); // 爆発しない
  expect(sim.totalResourceAmount()).toBeGreaterThan(0); // 食料が枯れ切らない
  expect(sim.decayedTileRatio()).toBeLessThan(0.5);     // 島が砂漠化しない
  expect(sim.stuckActors()).toHaveLength(0);            // 経路で詰まらない
  expect(sim.actorsOutOfBounds()).toHaveLength(0);
  expect(sim.sleepingRatioAtNight()).toBeGreaterThan(0.6); // 夜はちゃんと寝る
});
```

### 検証する不変条件

| 条件 | 意味 |
|---|---|
| 個体数が 40〜120 に収まる | 絶滅も爆発もしない |
| 資源総量が 0 にならない | 食料枯渇の永久ループがない |
| 荒廃タイル率 < 50% | 回復速度が消費に負けていない |
| 夜間の睡眠率 > 60% | 生活サイクルが成立している |
| 詰まりアクター 0 | 経路探索の不具合がない |
| NaN / 範囲外座標 0 | 数値計算の破綻がない |
| tick処理時間 p95 < 40ms | 負荷が許容内 |

CIでは3島日ぶん（約3.5万tick、数秒で完了）。
週1回、手動で30島日ぶんの長時間テストを流し、`/metrics` 相当のCSVを出力してグラフで確認します。

### fastForward の一致テスト

```ts
test('fastForwardは通常stepと大きく乖離しない', () => {
  const a = createSim({ seed: 's' }); for (let i=0;i<TICKS_PER_ISLAND_DAY;i++) a.step();
  const b = createSim({ seed: 's' }); b.fastForward(60 * 24);   // 島の1日ぶん
  // 完全一致は求めない。統計量が近いことを見る
  expect(ratio(b.critters.length, a.critters.length)).toBeCloseTo(1, 0.35);
  expect(ratio(b.totalResourceAmount(), a.totalResourceAmount())).toBeCloseTo(1, 0.4);
});
```

## 3. LLM関連のテスト

LLMは非決定的なので、**実APIを叩くテストは1本だけ**（疎通確認）に留めます。

| テスト | 方法 |
|---|---|
| プロンプト組み立て | 固定の世界状態から生成したプロンプト文字列をスナップショットテスト |
| トークン上限の遵守 | 記憶8件・会話3往復・summary400字の上限が守られているか（文字数アサート） |
| 出力検証 | enum外のgoal、存在しないtargetName、超長文、JSON崩れ、空文字を**モックで注入**し、必ずフォールバックすること |
| インジェクション耐性 | 攻撃文の固定リスト20件をモック経由で通し、サーバ状態が変化しないこと |
| フォールバック | `--llm=fail` モードで全機能が動作継続すること |
| レート制限 | 1分に100回 `say` を送り、実際のLLM呼び出しが予算内に収まること |
| 疎通（実API） | `tools/llm-smoke.ts`。CIでは実行せず、手動＋M0で1回 |

```ts
// 出力検証テストの例
test.each([
  { goal: 'DESTROY_ISLAND' },                   // enum外
  { goal: 'talk_to', targetName: '存在しない子' }, // 解決不能
  { goal: 'explore', reason: 'あ'.repeat(500) },  // 超長文
  {},                                            // 必須欠落
])('不正なintentは安全に落ちる %j', (bad) => {
  const intent = resolveIntent(bad as any, world, pet);
  expect(VALID_GOALS).toContain(intent.goal);
  expect(intent.reason.length).toBeLessThanOrEqual(60);
});
```

## 4. E2Eテスト（Playwright）

```ts
test('2人が同じ島で会い、ペットが応答する', async ({ browser }) => {
  const [a, b] = await Promise.all([browser.newContext(), browser.newContext()]);
  const pa = await a.newPage(), pb = await b.newPage();
  await pa.goto(URL + '?llm=mock'); await pb.goto(URL + '?llm=mock');
  await createPet(pa, 'mofi', 'モフィ'); await createPet(pb, 'mizune', 'ミズネ');
  await walkTo(pa, 64, 64); await walkTo(pb, 65, 64);
  await expect(pa.getByTestId('nearby-players')).toContainText('1');
  await say(pa, 'こんにちは');
  await expect(pa.getByTestId('chat-log')).toContainText('モフィ');
});
```

その他のE2Eシナリオ:

- 初回訪問 → タマゴ選択 → 島に入る までが完走する
- WSを切断（`context.setOffline`）→ 自動再接続してアバターが復帰する
- サーバ再起動を挟んでもプレイヤーとペットが失われない
- スマホビューポート（iPhone 14）でバーチャルパッド操作ができる

E2Eは常に `?llm=mock`（サーバも `--llm=mock`）で実行し、コストと不安定さを持ち込みません。

## 5. 見た目の回帰確認

- `?tool=sheet` にすべてのアセットを並べる開発用ページを用意
- Playwrightで撮影 → `tests/e2e/__screenshots__/` と比較
- 差分が出たら人間が目で確認して承認（自動失敗にはしない。絵は意図的に変わるため）

## 6. 負荷テスト

`tools/loadtest.ts`：WSクライアントを16本立ててランダム操作を送り続ける。

| 指標 | 目標 |
|---|---|
| tick処理時間 p95 | < 40ms |
| 送信バイト/秒（サーバ合計） | < 200KB/s |
| サーバRSS | < 400MB（1時間稼働後も増え続けないこと） |
| クライアントfps（16人が画面内） | PC 60 / スマホ 30 |

## 7. 品質の運用ルール

- `npm run typecheck` は `strict` ＋ `noUncheckedIndexedAccess` で通す
- 受信データは**必ずzodでparse**。`as` によるキャストで境界を越えない
- `island_event` / `chat_log` / `llm_usage` は消さない（挙動がおかしいときの唯一の手がかり）
- バランス定数は `shared/constants.ts` に集約し、マジックナンバーをコードに散らさない
  → 調整時に1ファイル見れば済む状態を保つ
- コミット前: `npm run typecheck && npm test`
