# 11. リスクと決定事項

## 1. リスク一覧

| # | リスク | 影響 | 起きやすさ | 対策 |
|---|---|---|---|---|
| R1 | **LLMコストが想定を超える** | 高 | 中 | 動物住民はLLM不使用。ペットのみ・用途3種に限定。プレイヤー単位／島単位／グローバルの3段レート制限。`llm_usage` で常時可視化。不在時は間隔10倍 |
| R2 | **LLMのレイテンシで会話が「重い」** | 高 | 高 | ストリーミング必須。初トークン3秒でタイムアウト→定型セリフ。会話中は吹き出しに「…」を出して待ち時間を演出に変える |
| R3 | **ペットの発話が単調・記憶が効いていないように見える** | 高 | 高 | 記憶検索を「その場にいた出来事」に限定し、知っている/知らないの差を作る。日記による長期記憶。プロンプトに「知らないことは知らないと言う」を明記。M4完了条件に「さっき見た出来事に言及できる」を入れる |
| R4 | **生態シミュのバランスが取れない**（絶滅／個体爆発／砂漠化） | 高 | 高 | 決定論テストで不変条件を機械的に検証（`10_テストと品質.md`）。バランス定数を1ファイルに集約。7島日回して破綻しないまでM3を出ない |
| R5 | **動物120体＋16人でtickが間に合わない** | 中 | 中 | 行動再評価のtime slicing（1個体2秒ごと）、A*のキュー制限、フローフィールド共有、興味管理。`/metrics` でp95監視。ダメなら個体数を下げる |
| R6 | **アセットの絵柄が揃わない／枚数が多すぎる** | 中 | 高 | 共通スタイル句の固定とプロンプト台帳。ポーズシート単位の生成（約150回に圧縮）。プレースホルダで開発を先に進める |
| R7 | **プロンプトインジェクションでペットが壊れる／不適切発言** | 中 | 中 | LLM出力に権限なし（enum＋名前解決のみ）。噂は「誰かの発言」として渡す。入出力のNGワードフィルタと全件ログ |
| R8 | **オフライン進行が破綻する**（放置後に世界が壊れている） | 中 | 中 | `fastForward` を通常stepと別実装＋一致テスト。上限24島時間 |
| R9 | **単一プロセス障害で島が消える** | 中 | 低 | 30秒スナップショット＋WAL。記憶と会話は即時書き込み。日次でDBファイルをコピーバックアップ |
| R10 | **`gpt-5.6-luna` が想定パラメータに非対応**（`temperature` / `json_schema` / `stream`） | 中 | 中 | M0で `llm-smoke` により確認。`llm/client.ts` に capability フラグを持たせ、起動時プローブで分岐。json_schema非対応なら「few-shot＋JSON.parse＋zod再試行」に落とす |
| R11 | **匿名認証でアカウントが失われる**（localStorage削除） | 低 | 中 | 復元コード（secretを人が読める12文字に変換）を設定画面に表示し、別ブラウザで入力可能にする |
| R12 | **スマホで重い／操作しづらい** | 中 | 中 | 早い段階（M2）で実機確認。パーティクル削減、resolution上限、タップ判定拡大 |
| R13 | **面白くない**（自律してるのが伝わらない） | 高 | 中 | 「留守中サマリ」と「ペットの噂報告」を体験の中心に置く。M4時点で他人に触ってもらいフィードバックを取る |

### 特に注意すべき失敗の形

R3とR13は技術的には成功していても**体験として失敗する**タイプです。
「ペットが自分で考えている」と感じさせるのは、賢い応答よりも
**プレイヤーが知らないことをペットが知っている**という非対称性です。
そのため、記憶を「その場にいた出来事だけ」に限定する設計（`04_サーバ設計.md` §5）は
最適化ではなく**面白さの中核**として扱います。

## 2. 決定事項（ADR）

### ADR-001: 動物住民はLLMを使わない

- **決定**: 動物住民の行動はユーティリティAI。LLMはペットのみに使う。
- **理由**: 120体×LLMは費用・レイテンシ両面で成立しない。「自律している」の説得力は
  行動の一貫性（生活サイクル・関係性・世代交代）から出るもので、自然言語生成は必須でない。
- **代償**: 動物はしゃべらない。→ 動物の「気持ち」は絵とアイコン、および
  ペットの口を通した通訳（「ハッカがおなかすいたって」）で表現する。

### ADR-002: シミュレーションは同期・LLMは非同期

- **決定**: tickループ内でLLMを待たない。intentキュー経由で結果を受け取る。
- **理由**: LLMのレイテンシ（数秒）がゲーム全体のフレーム落ちになるのを防ぐ。
  LLMが完全に落ちてもゲームは動き続ける必要がある。

### ADR-003: 記憶検索に埋め込みを使わない

- **決定**: 「新しさ＋重要度＋キーワード一致」のスコアで選ぶ。
- **理由**: 埋め込みAPI呼び出しとベクトル検索の追加は、記憶件数（1ペットあたり数千件）に対して過剰。
  固有名の辞書はシミュレーション側が持っているのでキーワード一致が実用的に機能する。
- **再検討条件**: 記憶が1ペット1万件を超え、キーワード一致の精度不足が体感できたとき。

### ADR-004: SQLite（単一プロセス常駐）

- **決定**: better-sqlite3 ＋ メモリ上の状態が正。
- **理由**: 1島16人の規模でRDBMSを立てる理由がない。運用がファイル1個で済み、バックアップも `cp` で足りる。
- **再検討条件**: 島インスタンスを複数ホストに分散する必要が出たとき（→ Postgres＋Redis）。

### ADR-005: プロトコルはJSONから始める

- **決定**: MVPはJSONテキストフレーム。MessagePackは後回し。
- **理由**: 見積り帯域は16人で60KB/s程度であり、最適化の前に可読性を取る。
  デバッグ時にDevToolsでそのまま読めるのが大きい。
- **再検討条件**: 送信バイト/秒が200KB/sを超えたとき。

### ADR-006: デプロイは単一VPS＋常駐プロセス

- **決定**: 1台のLinuxホストで systemd により常駐、Nginxでリバースプロキシ（WS対応）＋TLS。
  クライアントの静的ファイルも同一ホストから配信。
- **理由**: 「サーバが常に動いていて島の時間が進んでいる」がゲームの前提であり、
  サーバレス（コールドスタート・実行時間制限）と相性が悪い。
- **代償**: スケールアウトは手動。→ 島インスタンスをプロセス単位で増やし、
  ロビーが空きのある島へ振り分ける方式で当面は足りる。

### ADR-007: UIはDOM、ゲーム世界はPixi

- **決定**: チャット・設定・サマリはHTML/CSS。UIフレームワークは入れない。
- **理由**: 日本語入力（IME）・折返し・スクリーンリーダー対応をCanvasで再実装するのは損。
  画面数が少ないためReact等の状態管理も不要。

## 4. 中止・縮小の判断基準

以下に該当したら、機能を削って**「島が自律している」の1点に集中**します。

- M3のバランス調整が5日を超えても収束しない → 動物の種類を3種に減らし、繁殖を一旦切る
- M4のLLMコストが1プレイヤー1時間で想定の3倍を超える → 会話を1島日あたり回数制で提供する
- アセット生成が絵柄の一貫性を保てない → 種類を減らし、色替えバリエーションで水増しする
