# 04. サーバ設計（島シミュレーション）

## 1. tickループ

```
TICK_HZ = 4          → 1tick = 250ms
BROADCAST_HZ = 4     → 毎tickブロードキャスト（差分のみ）
SNAPSHOT_INTERVAL = 120 tick（30秒）
```

`setInterval` ではなく「遅れを検出して詰める」ループにします。GCやLLMのマイクロタスクでtickが遅れても島時間がズレないようにするためです。

```ts
// sim/island.ts
export class IslandSim {
  tick = 0;
  private accumulatorMs = 0;
  private lastMs = 0;

  start() {
    this.lastMs = performance.now();
    const loop = () => {
      const now = performance.now();
      this.accumulatorMs += now - this.lastMs;
      this.lastMs = now;

      let steps = 0;
      while (this.accumulatorMs >= TICK_MS && steps < MAX_CATCHUP_STEPS) {
        this.step();                 // 固定ステップ
        this.accumulatorMs -= TICK_MS;
        steps++;
      }
      if (steps === MAX_CATCHUP_STEPS) {
        // 追いつけていない = 負荷過多。警告を出し余剰を捨てる
        this.accumulatorMs = 0;
        metrics.tickOverrun++;
      }
      setTimeout(loop, Math.max(0, TICK_MS - (performance.now() - now)));
    };
    loop();
  }
}
```

### step() の中身（順序が意味を持つ）

```ts
step() {
  this.tick++;
  this.clock.advance(this.tick);          // 1) 時間・季節・天気
  this.resources.update(this.tick);       // 2) 資源の回復・荒廃度の減衰
  this.needs.update(this.tick);           // 3) 全アクターの欲求を増加
  this.critterAI.update(this.tick);       // 4) 行動の選択（一部個体のみ／後述）
  this.petActions.update(this.tick);      // 5) ペットのintentを行動へ変換
  this.movement.update(this.tick);        // 6) 経路に沿って移動・衝突解決
  this.interactions.update(this.tick);    // 7) 行動の完了判定と効果適用
  this.relations.update(this.tick);       // 8) 好感度・繁殖・寿命（低頻度）
  this.events.flush();                    // 9) 発生イベントをDB/記憶/通知へ
  this.sync.broadcast(this.tick);         // 10) 差分送信
  if (this.tick % SNAPSHOT_INTERVAL === 0) this.repo.saveSnapshot(this);
}
```

### 負荷分散（time slicing）

動物120体の行動再評価を毎tick全員に行う必要はありません。
`id % 8 === tick % 8` の個体だけを評価し、**1個体は2秒ごと**に判断を更新します。
移動と衝突は全員毎tick（滑らかさに直結するため）。

## 2. ワールドクロック

```ts
ISLAND_DAY_MINUTES = 60;                        // 実時間60分 = 島の1日
TICKS_PER_ISLAND_DAY = 60 * 60 * TICK_HZ;       // 14400 tick
// 朝 0..25% / 昼 25..55% / 夕 55..75% / 夜 75..100%
DAYS_PER_SEASON = 7;
```

- 天気は島日の切り替わりで季節別テーブルから抽選。さらに1島時間ごとに10%の確率で遷移する。
- 天気と時間帯は行動ユーティリティの係数として全システムから参照される（雨→屋外行動-30%、夜→sleep重み+50%）。

### 季節テーブル（初期値。要バランス調整）

| 季節 | 資源回復倍率 | 天気（clear/cloudy/rain/fog） | 出生率倍率 |
|---|---|---|---|
| 春 | 1.3 | 45/30/20/5 | 1.8 |
| 夏 | 1.1 | 60/20/18/2 | 1.0 |
| 秋 | 1.5 | 50/30/15/5 | 0.8 |
| 冬 | 0.5 | 35/35/15/15 | 0.2 |

冬は食料が減るため空腹由来のケンカが増え、宣伝資料の「実りが少ない年はケンカも増える」が自然に成立します。

## 3. 島の生成（worldgen）

seedから決定論的に生成します。

1. value noise（PRNGベース、外部ライブラリ不要）で高度マップを作る
2. 高度 <0.30 → water、<0.36 → sand、<0.70 → grass、それ以上 → forest
3. 中心付近の平坦域を `plaza`（広場）にする ＝ プレイヤーのスポーン地点
4. forestに `berry_tree` を密度0.06で配置、grassに `field` を数箇所、waterの縁に `fishing_spot`
5. 島の外周1タイルは常にwater（境界処理を単純化）
6. 動物を種ごとの好適地形に散布し、`traits` をPRNGで生成

生成結果はチャンク単位でクライアントへ配信（`05_通信プロトコル.md`）。

## 4. 動物のユーティリティAI

LLMを使わず「それっぽく生きている」を作るための中核です。

### スコアリング

各tickの評価対象個体について、候補行動ごとにスコアを計算し最大のものを選びます。
ヒステリシス（現在の行動には+15のボーナス）を入れて、行動がちらつくのを防ぎます。

```ts
type Candidate = { kind: ActionKind; target?: EntityId | Vec2; score: number };

function scoreEat(a: Actor, w: World): Candidate | null {
  const food = w.findNearestResource(a.pos, ['berry_tree', 'field'], a.searchRadius());
  if (!food || food.amount <= 0) return null;
  const need   = curve(a.needs.hunger);                 // 0..1（切迫で急上昇）
  const dist   = falloff(distance(a.pos, food.pos), 20);
  const trait  = 0.6 + a.traits.gluttony * 0.8;
  const weather = w.weather === 'rain' ? 0.7 : 1;
  return { kind: 'eat', target: food.id, score: 100 * need * dist * trait * weather };
}
```

| 行動 | 主要因 | 補正 |
|---|---|---|
| `eat` | 空腹 × 資源の近さ | 大食い性格、雨で減衰 |
| `drink` | 空腹の副次（渇き値は持たない） | 水場の近さ |
| `sleep` | 眠気 × 夜であること | 巣の近さ、雨なら林の下 |
| `socialize` | 社交欲 × 好感度の高い相手の近さ | 社交性traits、広場/ベンチで加点 |
| `flee` | 近くの脅威（大型個体・プレイヤーの急接近） | caution traits |
| `nest` | 眠気＋安全欲、巣を持っていない | 季節（春に加点） |
| `wander` | 常に低い基礎値 | curiosity traits、未訪問タイルへ誘引 |
| `goto`（設置物） | 設置物のattract値 | 天気・時間帯 |

### 移動と経路探索

- タイルグリッド上のA*。ただし毎tick全員がA*を走ると重いので、
  **距離12タイル以内は直進＋壁沿い滑り**、それ以上はA*（1tickあたり最大8リクエストのキュー処理）。
- よく使われる目的地（広場・水場）へは**フローフィールド**を島日ごとに1回作って共有する。
- 衝突は円半径0.35タイルの押し出しのみ（物理エンジンは入れない）。

### 関係性・世代交代（低頻度システム）

`relations.update()` は 20tick（5秒）ごとに実行。

- 近接（2タイル以内）かつ双方awakeで `socialize` 中 → 好感度 +0.5（traitsで増減）
- 同じ資源を取り合った → 好感度 -2、確率でイベント `quarrel` 発生
- 島日切り替え時：
  - 全個体 `ageDays += 1`
  - 成体ペア（好感度 > 60、同種、season出生率）→ 子個体を生成。traitsは親平均＋±0.1のノイズ
  - `ageDays > lifespanDays` → `died` イベントで退場（死体は残さない。「巣に帰った」表現にする）
  - 個体数上限（120）に達している場合は出生を抑制

これらはすべて `island_event` に記録され、ペットの記憶素材になります。

## 5. イベントバス

```ts
export interface IslandEvent {
  kind: 'born'|'died'|'quarrel'|'befriend'|'harvest'|'build'|'weather'|'player_say'|'pet_say';
  tick: number; actorId?: EntityId; targetId?: EntityId; pos?: Vec2;
  text: string;          // 日本語1文
  importance: number;    // 1..10
}
```

`flush()` の処理:
1. DBの `island_event` へバルクinsert
2. **近くにいた（10タイル以内）ペット**の `pet_memory` に `kind='observe'` で複写
   → 「その場にいた記憶」だけが残るので、ペットごとに知っていることが違う
3. 接続中クライアントに通知が必要なもの（自分の近くの出来事）をブロードキャスト
4. importance >= 6 のものは留守中サマリ用に保持

## 6. オフライン進行とcatch-up

サーバは常駐前提ですが、再起動やデプロイで止まります。

起動時に `island.updated_at` と現在時刻の差 `Δ` を見て:

| Δ | 処理 |
|---|---|
| < 1分 | そのまま再開 |
| 1分〜24島時間 | **圧縮シミュレーション**：1ステップ=1島分（240tick相当）の粗い更新をΔ分だけ回す。移動は行わず、欲求・資源・関係・世代のみ更新し、代表的なイベントを生成 |
| > 24島時間 | 24島時間ぶんだけ圧縮実行し、「島は少し眠っていた」扱いにする |

圧縮シミュレーションは通常の `step()` とは別関数 `fastForward(islandMinutes)` として実装し、
決定論テストで「24時間早送りしても資源が枯渇/爆発しない」ことを検証します（`10_テストと品質.md`）。

## 7. graceful shutdown

```
SIGTERM/SIGINT →
  1) 新規接続を停止
  2) 全クライアントに { type:'serverClosing' } を送る
  3) tickループ停止
  4) saveSnapshot + island更新 + WALチェックポイント
  5) 進行中のLLMリクエストを中断（AbortController）
  6) exit
```

## 8. 観測（メトリクス）

- tick処理時間の p50/p95、overrun回数
- 動物数・出生数/死亡数（直近7島日）
- 資源の総量推移、荒廃タイル率
- 接続数、送信バイト/秒
- LLM: purpose別のRPM・p95レイテンシ・失敗率・累積トークン
