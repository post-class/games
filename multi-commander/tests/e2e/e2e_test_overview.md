# multi-commander

## 依頼概要
playwright-headless MCP を使用してE2Eテストを実施してください。
単体テストで実施できる項目（テストコードでテストできる）は、E2Eテストの対象外です。

## 手順

### 1. テストケースの作成
- tests/e2e/yyyyMMdd/ というフォルダを作成し、テストケースを作成してください。
- 「テスト観点」セクションの観点を網羅するように、テストケースを起こしてください。
- 全画面のキャプチャを取得して想定通りであること
- 全画面において、全ボタンを押下して、想定通りであること
- 全画面において、全てのキーボード操作およびオペレーションを行い、想定通りであること
- シナリオテストも実施すること

#### 入力操作の判定ルール

- 「イベントを送信できた」だけでは PASS にしない。各入力を単独で実行し、操作前後の HUD またはゲーム状態の変化を確認する。
- 各入力ケースには、初期状態、実行イベント、期待する状態変化、画面上の確認項目、失敗時の証跡を記録する。
- 同じ結果を複数の入力で作れる場合は、入力元を識別できる初期値を設定し、入力ごとに個別の前後値を記録する。
- キー入力は単発タップ、押しっぱなし、キーリピートを別ケースとして扱う。`page.keyboard.press()` だけで押しっぱなしを代用しない。
- 実ブラウザの DOM 経路を検証する入力では、合成 `dispatchEvent` だけで判定しない。キーボードは `page.keyboard`、ポインターは `page.mouse`、ホイールは対象要素上の `page.mouse.wheel()` を使う。
- 数値を正確に比較する必要がある場合は、読み取り専用のゲーム状態を補助的に取得してよい。ただし、最終判定には HUD など画面上の反映も含める。テスト中に状態を直接書き換えてはならない。
- 発艦などの入力上書き演出がある場合は、演出終了を確認してから入力ケースを開始する。今回のゲームでは `window.__mc.game.deck.phase === 'none'` を待機条件とする。
- 期待する状態変化が確認できない場合は FAIL、確認方法自体が成立しない場合は未検証とし、操作実施だけを理由に PASS にしない。

### 2. テスト実施
- サブエージェントを使って並列でテスト実施する
- playwright-headless MCP を使用する
- エビデンスは tests/e2e/yyyyMMdd/ に保存する（サブディレクトリ作成する）
- 結果はテストケースを更新する

### 3. 修正 再テスト
- テスト結果を元に、修正を実施する
- 並列動作可能な部分は、サブエージェントを活用する
- 再テストは、並列動作可能なため、サブエージェントを活用する
- 再テストOKとなるまで、修正とテストを繰り返す

## テスト観点

1. **画面表示**：実画面の文字、画像、レイアウト、選択状態、文字切れ、文字化けを確認する
2. **表示の重なり**：画面端で切れず、HUDや他要素、ポップアップに隠れないことを確認する
3. **viewport対応**：複数解像度、縦横比、縦長・横長、モバイル相当で確認する
4. **overflow・スクロール**：意図しない横スクロールがなく、必要な項目へ到達できることを確認する
5. **ボタン・メニュー**：全項目の表示、有効／無効状態、選択、クリック結果を確認する
6. **画面遷移**：開始、戻る、閉じる、キャンセル、再開、タイトル復帰を実操作で確認する
7. **キーボード操作**：矢印、WASD、Enter、Space、Escape、Tab、数字、割り当て変更を確認する
8. **ポーズ画面**：ESC後に全ボタンが見え、隠れず、ポーズ中にゲームが進まないことを確認する
9. **マウス・タッチ操作**：移動、左右クリック、ホイール、ドラッグ、タップ、タッチ相当操作を確認する
10. **入力の重なり**：透明要素、画面端、スクロール領域、`z-index`、`pointer-events`による操作阻害を、実際の DOM イベント経路で確認する
11. **ゲームパッド未接続**：対象外の場合も、未接続時にエラーや画面停止がないことを確認する
12. **戦闘プレイ**：移動、ターゲット、武器、弾切れ、被弾、損傷、撃墜、脱出、帰投を実プレイで確認する
13. **シナリオプレイ**：任務達成、未達、失敗、中断、デブリーフ、再挑戦を一連の操作で確認する
14. **キャンペーン導線**：勝利、敗北、終端、追悼、授与式、各ゲームモードを画面操作で確認する
15. **時間経過・自然発生**：待機による敵出現、AI反応、同時イベント、自然発生イベントを確認する
16. **保存・復元操作**：新規、続きから、保存、ロード、上書き、空データ、再読み込みを確認する
17. **画面上の設定保持**：設定、進行状況、スコア、資源、名簿、戦績が画面上で意図どおり保持されることを確認する
18. **ブラウザ・リソース異常**：アセット404、ネットワーク切断、fatal error、画面停止からの復帰を確認する
19. **アクセシビリティ操作**：見出し、ラベル、無効状態、キーボードだけでの操作性を確認する
20. **E2E証跡・判定**：操作前後の画面、viewport、再現条件、スクリーンショット、結果を記録する

### 入力操作で必須とする追加確認

- 各操作を単独で実行し、操作前後の値または表示を記録する。HUD の最終値だけで入力元を推測してはならない。
- `]` / `[` は単発タップと押しっぱなしを分ける。単発タップは1回で期待値が変化すること、押しっぱなしは時間経過に応じて連続変化することを確認する。
- 数字キーの直接指定と、増減キーの相対変更を分ける。例として `0% → ] 1回 → 10%`、`10% → [ 1回 → 0%`、`0% → 5 → 50%` を記録する。
- ホイールはゲームの入力対象（canvas）上で上下に1回ずつ操作し、`±10%` の変化、`preventDefault`、意図しないスクロールがないことを確認する。
- `#overlay` が `pointer-events: none` でも、canvas が実際の入力対象としてイベントを受けることを確認する。透明な UI の存在だけで PASS にしない。
- 発艦演出終了後に入力を開始し、演出による入力値の上書きと実入力の失敗を混同しない。
- コンテキストメニュー抑止、横スクロール抑止、コンソールエラーの有無を入力ケースの結果に記録する。

※ 純粋な計算、個別関数、内部データ構造、AIやゲームルール単体の網羅、入力値の組み合わせだけで完結する検証は単体テストの対象とし、ここには含めない。
