# Multi-Commander 共通コーディング注意点

このファイルは、今後の実装・修正・テストで共通して守る注意点をまとめたものです。

## 基本方針

- ユーザーとの会話・コメント・確認結果は日本語で記載する。
- 作業開始前に、リポジトリ直下と親ディレクトリの `AI_CODING.md`、および対象機能の既存実装・テストを確認する。
- 一時ファイル、ログ、スクリーンショットは `.tmp/` 配下に置く。
- 作業前後に `git status` と差分を確認し、依頼対象外の変更を上書き・削除しない。`git reset --hard` や無断の `git checkout` は使用しない。
- 編集は `apply_patch` を使用し、既存の設計や命名を尊重する。大規模な置換は、変更範囲を確認してから行う。

## 実装時の注意

- 既存の入力、HUD、チュートリアル、難易度、ロードアウトの責務を混ぜない。共通化する場合も、通常プレイ用とチュートリアル用の固定値・状態は分離する。
- 難易度補正は対象を明確にする。プレイヤー攻撃だけの補正を敵の攻撃へ誤適用せず、NORMAL/HARD の既存挙動を変えない。
- 難易度で挙動を免除する場合は、対象（誰の・どの経路の）をコメントで限定し、NORMAL / HARD の数値は変えない。
- 半透明な内装・エフェクトを足すときは `depthWrite: false` を検討し、背後の機体・弾が消えないことを実機で確認する。
- 人間が読む文字列（用語）を変えるときは、内部識別子（`throttle` など）を変えない。保存データ・イベント名・テストの期待値へ波及させない。
- 実際の弾速・当たり判定・弾数と、HUD、照準、ブリーフィング、格納庫に表示する値は同じ設定値から生成する。表示だけ変えて実挙動が変わらない状態を作らない。
- 弾数を増やす場合は、搭載数・補給在庫・出撃時の消費・補給上限を一緒に確認する。無限補給や表示値だけの増加を許さない。
- 入力を受け付ける前提条件（発艦演出終了、`deck.phase === 'none'`、対象画面が表示中など）を明示し、状態遷移中に入力が上書きされないようにする。
- チュートリアルは「操作イベントを受け取った」だけで完了扱いにしない。仕様に応じて、操作後のゲーム状態・HUD値・表示内容を確認する。タイマー進行や最終ステップからのループなど、時間条件も実時間で確認する。
- キー操作では単発入力、押しっぱなし、キーリピートを区別する。エッジ入力を意図する操作を `keydown` の連続発生で複数回処理しない。
- UIの表示切替キーを追加するときは、既存の `X`、`D`、`N` などの操作と衝突しないこと、リセット時の初期ページが仕様どおりであることを確認する。

## 入力経路とブラウザ確認

- ブラウザ確認は Playwright MCP を使用する。SPA の確認では、ページを開いた後に snapshot で表示内容を確認する。
- `dispatchEvent` だけで入力テストを PASS にしない。キーボードは実キー入力、ホイールは対象 canvas 上への `page.mouse.wheel()`、クリックは実際の要素への操作で確認する。
- 各操作は、操作前の値、実行イベント、操作直後の期待値、画面上の反映を個別に記録する。「イベントを送信できた」だけでは PASS にしない。
- canvas と overlay の重なりを確認する。入力対象の `pointer-events`、overlay の `pointer-events: none`、`preventDefault`、context menu、意図しないページスクロールを確認する。
- 開発サーバーが停止している場合は再起動してから確認する。ポートが使用中の場合はプロセスと作業ディレクトリを確認し、無関係なプロセスを停止しない。必要なら別ポートで起動する。
- 画面レイアウトを変更した場合は、少なくとも 1280×720 で確認する。`scrollWidth` / `scrollHeight`、`clientWidth` / `clientHeight`、要素の矩形を確認し、不要なスクロールバーや枠外へのはみ出しを見逃さない。
- コンソールエラー、ネットワークエラー、context menu、ブラウザ全体の意図しないスクロールがないことを確認する。

## テストの書き方

- E2E仕様書では、操作一覧だけでなく、各ケースに「初期状態」「イベント」「期待する状態変化」「画面確認」「失敗時の証跡」を書く。
- 同じ結果を複数の入力で作れる場合は、入力元を識別できる初期値を設定し、各入力を単独で検証する。
- 単体テストは計算・状態遷移・境界値を検証し、E2Eテストは実DOMのイベント経路とHUDへの反映を検証する。内部状態の直接注入は補助検証に限定する。
- テストが失敗したときは、今回の変更による失敗か、既存のベースライン失敗かを切り分ける。既存の全テストを無関係に修正して結果を隠さない。
- テストを追加する際は、`tests/ut` から `src` を参照する相対パスを確認する。既存テストに誤った `../src` があっても、今回のテストは正しい `../../src/...` を使用する。
- 最低限、変更後に `npx vite build`、関連する単体・E2Eテスト、`git diff --check` を実行する。失敗を残す場合は、原因と既知のベースライン失敗を最終報告に記載する。

## UI・HUDの注意

- 画面の高さが小さい場合でも、メイン視界・コクピット・チュートリアルメッセージが競合しないようにする。高さや幅を変更したら、狭い画面と標準画面の両方を確認する。
- スクロールバーを廃止する場合は、単に `overflow: hidden` にせず、ページ分割・文字量・行間を調整して情報が欠落しないようにする。
- HUDのページ状態、ダメージ表示、Navマップなどの表示状態は、開始・リセット・表示復帰時の初期化規則を明確にする。
- 表示テキストだけでなく、状態が更新された直後の値を検証する。最終値だけでは、どの入力が反映されたか判別できない場合がある。

## 完了条件

- 実装、型チェック／ビルド、関連テスト、ブラウザ確認を行い、結果を報告する。
- 未検証の項目、既知の失敗、環境上の制約を「完了」と混同しない。
- 変更ファイルと、ユーザーが再現・確認するための操作手順を簡潔に示す。
