# 07 技術仕様: メタ進行と物語 (Phase 7)

本紙は Phase 7 のみを対象とする。全体ロードマップと各Phaseの位置づけは `03_ロードマップ.md` を参照。Phase 6 (分岐キャンペーン/ミッション種別) は `06_技術仕様_コンテンツとAI.md` が担当し、本紙はその分岐グラフの上に「誰が」「どんな結末で」戦っているかを乗せる層——パイロット名簿・僚機・勲章・ミッション間の人間ドラマ・セーブ形式v2——を書く。

ウィングコマンダーの核は「勝っても負けても物語が進み、失った僚機は二度と戻らない」という一回性にある。現状の multi-dommander は `cleared: string[]` と `totalKills: number` しか永続化しておらず、僚機は毎ミッション `AllySpawn` として湧いて消えるだけの存在 (`src/game/mission/MissionDefinition.ts` の `AllySpawn`) で、名前も生死も引き継がれない。Phase 7 はこの「記憶を持たないキャンペーン」を「積み重なる戦争」に変える。

---

## 1. パイロット名簿とパーマデス僚機

### 目的
プレイヤー機だけでなく僚機に固有の名前・階級・累積戦果・生死を持たせ、一度戦死した僚機は以後のブリーフィングにも会話にも二度と現れないようにする。損失に重みを持たせることがウィングコマンダーらしさの根幹。

### 現状
- `src/game/mission/missions.ts:19-22` の `wingmen: AllySpawn[]` はミッション定義に直接ハードコードされた無名の機体で、`combatant: true` の3人称データしか持たない。
- `src/game/mission/MissionDefinition.ts` の `AllySpawn` に `tag?: string` はあるが個体識別用ではなく護衛対象タグ用。
- 僚機が撃墜されてもゲーム側は何も記録しない (`MissionManager` のAI撃墜処理はセッション内のみ)。
- `SaveManager.ts:2-8` の `SaveData` にパイロット/僚機の概念が存在しない。

### 技術方針
- 「名簿 (Roster)」をキャンペーン単位の永続データとして `SaveDataV2.roster: Wingman[]` に持つ。各僚機は `id` で一意化し、ミッション定義側は `wingmen: AllySpawn[]` の代わりに `wingmen: WingmanSlot[]`（`rosterId` 参照 + スポーン位置）を持つよう `MissionDefinition` を拡張する。
- ミッション実行時、`MissionManager` は `rosterId` から名簿を引き、生存者のみスポーンする。名簿上で `status: "kia"` (戦死) の僚機は該当ミッションにスポーンさせず、代替不在時は素通り（穴が空いたまま出撃、緊張感の演出）にする。これは Phase 6 のミッション生成ロジックとインターフェースを合わせる必要があるため、`06` 側とスロット命名 (`rosterId`) を共有する。
- 戦死判定は既存の撃墜イベントに便乗する。僚機の艦体を表すエンティティに `rosterId` コンポーネントを付与し、破壊イベント発生時に `GameController` (または新設の `CampaignService`) が名簿を更新して `status = "kia"`、`killedInMission`、`killedAt` を記録する。パーマデスは「その場のセッション内で終わり」ではなく「名簿に書き込まれ、次回起動後も戻らない」ことが要件なので、更新は撃墜確定時点で即座に行い、ブリーフィング遷移時のセーブ (`GameController.ts:104-109` 相当) で永続化する。
- 名簿には性格タイプ (`personality`) を持たせ、会話シーン (§3) の台詞バリエーション選択に使う。性格は数値化せず固定enum (`hotshot` | `veteran` | `rookie` | `wisecrack` など) で足りる。演出は台詞側で吸収する。

### タスク分解
1. `Wingman` 型と `roster` を `SaveDataV2` に追加 (§6のスケッチ参照)。
2. `MissionDefinition.wingmen` を `AllySpawn` 直書きから `rosterId` 参照に変更 (既存3ミッションのデータ移行込み)。既存の `combatant`/`position` はスロット側に残す。
3. 僚機エンティティに `rosterId` タグコンポーネントを追加し、破壊時フックで `CampaignService.reportWingmanLost(rosterId, missionId)` を呼ぶ。
4. 名簿の初期データ (キャンペーン開始時の固定僚機3〜5名、名前・性格プリセット) を `src/game/campaign/roster.ts` として新設。
5. ブリーフィング画面 (`MissionScreens.showBriefing`) に「出撃メンバー」欄を追加し、戦死者は「欠員」または過去の戦死ログとして表示。

### 受け入れ基準
- 僚機を撃墜されたミッションをクリアし、一度タイトルに戻って再度起動しても、その僚機はブリーフィングの出撃メンバー欄に出現しない。
- 同じ僚機が別ミッションでも同一の名前・性格で会話に登場する (会話文言側の参照キーが `rosterId` で一貫している)。
- キャンペーンをリスタートすると名簿は初期状態にリセットされる。

### リスク
- ミッション難易度がスロット数に依存する設計 (例: 護衛任務は僚機2機前提) だと、戦死で欠員が出た場合の難易度調整が必要。→ 欠員時は敵ウェーブ数を軽減する簡易バランサーを `06` 側と協議して用意するか、「欠員でも数的不利を受け入れる」仕様にするかを明示的に選び、後者を既定推奨とする(実装コスト低・緊張感が増す方向に働くため)。
- 全僚機が全滅すると出撃メンバー欄が空になる。最低1名は不死化する救済スロット (プレイヤー機のみで出撃可) を許容するか、ゲームオーバー的な「増援なし」エンディング分岐にするかを決める必要がある。推奨は後者(キャンペーン失敗エンドとして処理)。

## 2. 勲章・階級・累積撃墜数

### 目的
ミッションを重ねるごとに階級が上がり、特定の戦功で勲章が授与される「昇進と勲章の授与式」演出を用意する。ウィングコマンダーはこれを task-force全体の戦況とプレイヤー個人の武勇の両方に紐づけていた。

### 現状
- `GameController.ts:22` の `totalKills` のみが累積値。階級・勲章は概念として存在しない。
- `GameStateData` (`GameState.ts:6-13`) はミッション単位の一時状態のみで、恒久成長要素を持たない。

### 技術方針
- `Rank` と `Medal` をデータテーブルとして定義し、`SaveDataV2.pilot` に `rank: RankId` と `medals: MedalAward[]` を持たせる。
- 階級は撃墜数やクリア数を閾値としたシンプルな関数 `computeRank(pilot: PilotRecord): RankId` で毎ミッション終了後に再評価する。閾値テーブルは `src/game/campaign/ranks.ts` に定数で置く (ロールプレイ的な複雑な経験値システムは不要、ウィングコマンダー同様「積み上げたら勝手に上がる」でよい)。
- 勲章は「条件付きトリガー」を持つデータ (例: `"護衛ミッションで護衛対象の被害0でクリア"`, `"通算撃墜30"`, `"僚機を全員生還させてキャンペーン完走"`) をミッション結果評価時にチェックし、条件を満たしたら `medals` に追加する。条件式は複雑にせず、`(ctx: DebriefContext) => boolean` の関数配列で十分。
- 昇進・勲章の授与は即座にデブリーフ画面へ差し込むのではなく、次のブリーフィングに入る前の「授与式シーン」(§3のシーン再生機を再利用) として表示する。ウィングコマンダーの「基地に戻ると司令官から勲章を渡される」体験に合わせ、報酬告知と物語のテンポを分離する。
- 累積撃墜数は既存の `totalKills` を `pilot.totalKills` に移し、`cleared` は `campaignState.cleared` に移す (そのままフィールド名維持で移行コストを下げる)。

### タスク分解
1. `Rank`/`Medal` の型とテーブルを新設 (`src/game/campaign/ranks.ts`, `src/game/campaign/medals.ts`)。
2. `proceed()` (`GameController.ts:144`) の成功パス内に `evaluateMedals()` / `computeRank()` 呼び出しを追加し、新規獲得があれば授与式シーンをブリーフィング前に挿入。
3. `MissionScreens` に授与式カード表示 (階級章アイコン代替のテキストバッジ、勲章名+説明) を追加。
4. デブリーフ画面 (`MissionScreens.showDebrief`) に現在階級を常時表示するよう軽微改修。

### 受け入れ基準
- 累積撃墜数が閾値を超えた次のブリーフィング前に昇進演出が一度だけ表示され、以後は表示されない(再表示防止フラグを名簿/pilotに保存)。
- 特定条件 (護衛任務ノーダメージ等) を満たしてクリアすると対応する勲章が名簿に記録され、キャンペーン完了後の実績表示 (§5) にも反映される。
- セーブをリロードしても既に授与された勲章・階級は保持される。

### リスク
- 勲章条件をミッションデータ非依存で書くと `06` のミッション種別追加時に判定が壊れる。条件関数は `DebriefContext` という共通インターフェース越しにのみミッション情報を読み、ミッション定義の内部構造に直接依存させないことで疎結合を保つ。
- 階級演出を毎回強制すると数分おきのテンポを阻害する。スキップキー (Enter即抜け) を必ず用意する。

## 3. ミッション間シーン: ブリーフィング室と酒場風の会話

### 目的
ミッション間に「肖像+台詞+選択肢」の会話シーンを挿入し、僚機との人間関係・戦死の余韻・選択による分岐フラグを演出する。ウィングコマンダーの司令官ブリーフィング、バーでの雑談、僚機の追悼はすべてこの一枚のUIパターンで再現できる。

### 現状
- `MissionScreens.ts:50-59` は `root: HTMLDivElement` 1枚に `innerHTML` を差し替える単純な画面遷移器で、キー入力は `handlers: Handlers` (1回押し) と `menu: MenuState` (矢印選択) の2モードしかない。
- 会話・肖像・選択肢の概念は皆無。`showBriefing`/`showDebrief` は静的テキストの表示のみ (`MissionScreens.ts:187-227`)。
- `screens.css` は目標リストやメニューのスタイルのみで、肖像や台詞ボックスの見た目は未定義。

### 技術方針
データ駆動の「シーン再生機」を `MissionScreens` に追加する。既存の「1回押しハンドラ登録」「MenuState矢印選択」の2パターンをそのまま使い、新しい `showDialogue(scene, onDone)` メソッドで両者を組み合わせる。

- **シーン定義** `DialogueScene` はビート (`DialogueBeat`) の配列。各ビートは「誰が」「どの表情/肖像で」「何を言うか」を持ち、任意で選択肢 (`choices`) を持つ。選択肢はビート単位の分岐であり、選択結果は `campaignState.flags` に書き込まれる (例: `flags.consoledRookieAfterLoss = true`)。この `flags` を Phase 6 の分岐条件やミッションのブリーフィング文言差し替えに使う。
- **再生ロジック**: `showDialogue` はビート配列を1件ずつ描画し、Enter/Spaceで「選択肢がなければ次のビートへ」、選択肢があれば既存の `MenuState` (矢印+Enter) に切り替えて選択後に次ビートへ進む。全ビート終了で `onDone(flags)` を呼ぶ。実装は `MissionScreens` 内に `private beats: DialogueBeat[] = []` と `private beatIndex = 0` を持つだけで、既存の `show()`/`showMenu()` の呼び出しを内部で使い分ければ大きな追加インフラは不要。
- **肖像表示**: 立ち絵アセットが無い前提でも成立するように、肖像は「テキストベースのアバターカード」(名前+階級+性格に応じた色帯、任意で1枚のポートレート画像 `portraitUrl`) とする。画像を用意できた段階で `portraitUrl` を差せば静止画肖像に自然に格上げできる設計にする。DOM構造は既存の `.screen-title`/`.screen-body` パターンに `.dlg-portrait` / `.dlg-speaker` / `.dlg-line` / `.dlg-choices` を追加するだけで、`screens.css` に以下相当のクラスを追記する:
  - `.dlg-portrait`: 左上に名前+階級バッジ、肖像画像 or イニシャル文字の色付き円。
  - `.dlg-line`: タイプライター風(任意, css transitionで十分)の台詞テキスト。
  - `.dlg-choices .opt.sel`: 既存 `.diff-opts .opt.sel` と同じ見た目を再利用。
- **挿入ポイント**: `GameController.toBriefing()` (`GameController.ts:94-114`) の直前、および `proceed()` (`GameController.ts:144-165`) の成功/失敗分岐直後にシーン挿入フックを設ける。具体的には:
  - デブリーフ直後、僚機が戦死したミッションでは「戦死報告シーン」を自動挿入 (追悼台詞、性格に応じたリアクション)。
  - ブリーフィング前、キャンペーン内の特定ノード (例: 中間ミッション後) で「酒場シーン」を挿入し、選択肢によって次ミッションの難易度アシストや勲章条件にフラグを反映。
  - シーンの有無・内容はミッション定義ではなく `src/game/campaign/scenes.ts` に `Record<string, DialogueScene>` (キーはキャンペーンノードID + タイミング `"pre" | "post"`) として持ち、`CampaignService` が該当キーを引いて有無を判定する (無ければスキップしてそのまま既存フローに落ちる=後方互換)。

### タスク分解
1. `DialogueScene`/`DialogueBeat`/`DialogueChoice` 型を新設 (§6参照)。
2. `MissionScreens.showDialogue(scene, onDone)` を実装 (既存 `show`/`showMenu` の合成)。
3. `screens.css` に肖像・台詞・選択肢のスタイルを追加。
4. `GameController` に `CampaignService`(新設、または既存クラスへの薄いメソッド追加) 経由でシーン挿入判定を追加。
5. 戦死報告シーンの自動生成ロジック (名簿更新イベントから `DialogueScene` を動的合成) を実装。
6. 初期キャンペーン用の会話データを3〜5シーン分 `scenes.ts` に書く (既存3ミッション構成に対応)。

### 受け入れ基準
- 僚機が戦死した次のブリーフィング前に、その僚機への言及を含む会話シーンが自動的に挿入される。
- 会話中の選択肢はキーボード (矢印+Enter) のみで完結し、既存のブリーフィング/デブリーフ画面と地続きの見た目・操作感を保つ。
- シーンが定義されていないノードでは何も挿入されず、既存のブリーフィング直行フローと完全互換。

### リスク
- 会話データが増えるとテキスト物量が肥大化し `scenes.ts` が巨大化する。ミッションデータと同様に「1ノード=1ファイル」split を早期に検討する(本紙は設計指針のみ提示し、分割自体は実装時タスク)。
- 動的合成する戦死報告シーンは、複数僚機が同時に戦死した場合の文言結合ロジックが必要。最初はビートを僚機ごとに1つずつ機械的に連結する単純な方式で十分(凝った文章生成は不要)。

## 4. アップグレード/経済 vs 固定進行 — 設計判断

### 目的
「機体・武装を資金で強化する経済システム」を入れるべきか、「固定進行+ストーリー的アンロック」にすべきかを決める。

### 検討
ウィングコマンダー本編はアーケード的な一本道進行で、プレイヤーが購入・改造できる経済システムを持たない (機体切り替えはミッション側が指定する)。一方 Privateer 系列や後発の翼商業action-RPGは経済システムを持つ。本プロジェクトが目指すのは「ウィングコマンダーと同等以上に面白い」ことであり、対象は経済シムではなく人間ドラマ主導のミリタリーキャンペーンである。

**賛成側の論点**: 経済/アップグレードは自由度とリプレイ性を与え、「弱い機体で無理をする」選択のドラマも生める。
**反対側の論点**:
- 経済バランス調整は独立したゲームデザイン作業であり、本ロードマップの他Phase (描画・AI・分岐ミッション) の工数を圧迫する。
- 難易度は既に `Settings.ts:12-19` の `DifficultyMods` で外側から制御されており、経済的な強化は難易度制御と機能が重複し設計が二重化する。
- ウィングコマンダーの面白さの核 (キャラの死、勝敗の重み、勲章) は経済に依存しない。Phase 7 の主眼をぶらさないためにも経済は後回しが適切。

**推奨**: **固定進行 + ストーリー的アンロックを採用し、購買型の経済システムは導入しない。** 具体的には:
- 機体・武装はミッション定義側 (`MissionDefinition.playerShipId`) が指定する一本道のまま維持する。
- 「アンロック」は資金ではなく「勲章/階級/キャンペーン進捗」に紐づける。例: 特定勲章を取得すると次回以降のブリーフィングで選べる僚機の性格バリエーションが増える、階級が上がると呼び出しコールサイン演出が変わる、等の**物語的ご褒美**に限定する。
- `unlocks: string[]` を `SaveDataV2` に持たせ、フラグの集合として管理する。UI上の「ショップ」画面は作らない。
- 将来的に経済要素を追加したくなった場合の拡張点として、`unlocks` を汎用フラグ集合にしておくことで後付けしやすくする(本Phaseでは実装しない)。

### 受け入れ基準
- 本Phaseの実装物に購入/ショップ画面が存在しないこと。
- `unlocks` フラグが勲章付与・キャンペーン分岐の到達によってのみ更新されること。

### リスク
- 後で経済を足したくなった場合、`unlocks` を真偽フラグ集合のまま使い続けると資源量(残弾・資金のような数値)の表現に向かない。数値経済を将来追加する場合は別途 `SaveDataV3` で `resources: Record<string, number>` を増設する前提を明記しておく。

## 5. 難易度/アシストの拡張とキャンペーン完遂後の「強くてニューゲーム」

### 目的
既存の3段階難易度をメタ進行と絡め、キャンペーン完遂後に緊張感を保ったまま再挑戦できる仕組みを用意する。

### 現状
- `Settings.ts:2-19` は `easy`/`normal`/`hard` の3値と `DifficultyMods` の敵性能倍率のみ。プレイ中変更不可、セーブとは独立 (`SettingsStore` は別キー `multidommander.settings.v1`)。
- `GameController.proceed()` (`GameController.ts:144-157`) はキャンペーン完全クリアで `SaveManager.clear()` してメニューに戻すだけ。「強くてニューゲーム」的な継続要素はゼロ。

### 技術方針
- 難易度に「アシストオプション」の概念を追加する。既存の `DifficultyMods` に手を加えず、`SaveDataV2.pilot.assists: AssistFlags` として直交させる (例: `autoLevelingAssist`, `targetLeadAssist` のような、Phase 1/2 の操作系実装と連携するフラグ)。本紙では枠のみ定義し、実際のアシスト効果の実装は該当Phase (操作・AI) 側の担当。
- キャンペーン完遂後、`SaveManager.clear()` で全消去する代わりに「エピローグシーン → 新しい周回 (NG+) 開始」を提供する。NG+では:
  - `roster` は初期化されるが、`pilot.rank`/`medals`/`unlocks` は保持する (= 積み上げた実績は残る)。
  - `campaignState` (分岐位置・クリア済みノード) のみリセットし、新しい周回の分岐結果を再度記録できるようにする。
  - 難易度は自動的に1段階格上げを提案する (プレイヤーが拒否できる選択肢付き)。
- NG+の周回回数を `pilot.ngPlusCount: number` として記録し、勲章条件やエピローグ文言の分岐に使う (例: 2周目クリアで専用勲章)。

### タスク分解
1. `AssistFlags` 型を `Settings.ts` 近傍に追加 (本Phaseでは型定義とセーブ連携のみ、効果実装は別Phase)。
2. `GameController.proceed()` のキャンペーン完全クリア分岐を「エピローグシーン表示 → NG+選択」に変更。
3. `SaveManager` に `startNewGamePlus(save: SaveDataV2): SaveDataV2` ヘルパーを追加 (roster/campaignStateのみ初期化)。
4. `showCampaignComplete` (`MissionScreens.ts:229-236`) をエピローグ+NG+選択の画面に拡張。

### 受け入れ基準
- キャンペーンを完遂すると、階級・勲章・アンロックを保持したまま次周回を開始できる選択肢が出る。
- NG+開始後、名簿は初期状態に戻るが `pilot.medals` は前回分を含めて表示され続ける。
- NG+を選ばず終了した場合、既存のセーブ削除+メニュー復帰のフローも維持する (完全クリア後に「もう一度最初から」を選べる)。

### リスク
- 難易度格上げの自動提案は`Settings.ts`の`DifficultyMods`にしか影響しないため、Phase 6のミッション生成ロジックが難易度以外の要素(敵数など)でNG+の手応え変化を作る場合は連携確認が必要。

## 6. セーブ形式v2: データモデルと移行

### 目的
現行の平坦な `SaveData` (missionId/totalKills/cleared) を、名簿・勲章・会話フラグ・進行状態を持つ `SaveDataV2` に置き換え、将来のスキーマ変更にも耐えるバージョン管理を導入する。

### 現状
`SaveManager.ts:1-41` 全体。`KEY = "multidommander.save.v1"` で無条件に保存/読込し、バージョンフィールドが無いため型不整合時の防御は `typeof data.missionId !== "string"` という弱いチェック1点のみ (`SaveManager.ts:19`)。

### 技術方針
- 保存キーは `v2` に切り替える (`multidommander.save.v2`)。v1キーは移行元として読むが、書き込みは常にv2キーへ行う。
- `SaveDataV2.version: 2` を必須フィールドとして持たせ、将来 v3 が来た際も `version` で分岐できるようにする。
- 読み込み時のロジックは「v2キーがあればそれを使う」「無ければv1キーを読み、あれば `migrate(v1)` してv2として保存し直す」「どちらも無ければ新規作成」の3分岐にする。

```typescript
// src/game/SaveManager.ts (刷新後のスケッチ)

/** キャンペーン内で戦死/生存を追う僚機データ。 */
export interface Wingman {
  id: string; // roster内で一意。missions.ts の wingmen スロットが参照する rosterId と同じ値域。
  name: string;
  callsign: string;
  personality: "hotshot" | "veteran" | "rookie" | "wisecrack";
  status: "active" | "kia" | "mia";
  killedInMission: string | null; // status=kia/mia のときの戦死ミッションID。
  killedAt: number | null; // simTime。
  kills: number; // この僚機自身の撃墜数 (会話文言のバリエーションに使用)。
  portraitUrl?: string; // 未設定時はイニシャル+性格色のアバターで代替。
}

export type RankId = "cadet" | "ensign" | "lieutenant" | "captain" | "colonel";

export interface Medal {
  id: string;
  name: string;
  description: string;
  awardedAt: number; // simTime。
  awardedInMission: string;
}

export interface PilotRecord {
  name: string;
  callsign: string;
  totalKills: number;
  rank: RankId;
  medals: Medal[];
  unlocks: string[]; // 勲章/階級/分岐到達で解放されるフラグ集合。経済的な数値資源は持たない (§4)。
  assists: Record<string, boolean>; // アシストオプション (効果は別Phase実装)。
  ngPlusCount: number;
}

/** 会話シーン中の選択で立つフラグ。Phase 6 の分岐条件からも参照される。 */
export type CampaignFlags = Record<string, boolean>;

export interface CampaignState {
  currentMissionId: string;
  cleared: string[];
  flags: CampaignFlags;
  /** 直近で提示済みの会話/授与式シーンキー (再表示防止)。 */
  seenScenes: string[];
}

export interface SaveDataV2 {
  version: 2;
  pilot: PilotRecord;
  roster: Wingman[];
  campaignState: CampaignState;
  updatedAt: number;
}

/** ミッション間会話シーンの定義。scenes.ts が Record<string, DialogueScene> として持つ。 */
export interface DialogueChoice {
  label: string;
  /** 選択時に campaignState.flags へ書き込むエントリ。 */
  setFlags?: CampaignFlags;
  /** 選択後に進むビートindex。省略時は次のビートへ。 */
  nextBeat?: number;
}

export interface DialogueBeat {
  speakerId: string | "narrator"; // roster の Wingman.id、または固定NPC ID、または narrator。
  speakerName: string; // roster解決前でも表示できるよう冗長に保持。
  portraitUrl?: string;
  lines: string[];
  choices?: DialogueChoice[];
}

export interface DialogueScene {
  id: string;
  beats: DialogueBeat[];
}

const KEY_V1 = "multidommander.save.v1"; // 移行元。読み取り専用。

/** v1 (missionId/totalKills/cleared) から v2 への移行。 */
function migrateV1toV2(v1: { missionId: string; totalKills: number; cleared: string[] }): SaveDataV2 {
  return {
    version: 2,
    pilot: {
      name: "Player",
      callsign: "ROOKIE",
      totalKills: v1.totalKills,
      rank: computeRank(v1.totalKills), // ranks.ts の関数を利用。
      medals: [],
      unlocks: [],
      assists: {},
      ngPlusCount: 0,
    },
    roster: INITIAL_ROSTER.map((w) => ({ ...w })), // roster.ts の初期名簿 (v1には無いため新規発行)。
    campaignState: {
      currentMissionId: v1.missionId,
      cleared: v1.cleared,
      flags: {},
      seenScenes: [],
    },
    updatedAt: Date.now(),
  };
}
```

- `SaveManager.load()` は戻り値を `SaveDataV2 | null` に変更し、内部でv1検出+移行を行う。呼び出し側 (`GameController`) のAPI形状 (`load()`/`save()`/`clear()`) は変えず、フィールドアクセスだけ `save.campaignState.currentMissionId` のように変わる。これにより `GameController.ts:82-92` の書き換え範囲を「フィールドパスの付け替え」に限定できる。
- 破損データ (JSONパース失敗、`version` 不一致で移行不能) は `null` を返し、呼び出し側の既存の「セーブが無ければ新規キャンペーン」フォールバック (`GameController.ts:49-60`) にそのまま乗せる。新規のバリデーションは `version` フィールドの型チェックを `typeof data.missionId !== "string"` (`SaveManager.ts:19`) の代わりに `data.version === 2 && typeof data.pilot?.name === "string"` 相当に強化する。

### タスク分解
1. 型定義一式 (`Wingman`, `PilotRecord`, `CampaignState`, `SaveDataV2`, `DialogueScene` 等) を `SaveManager.ts` もしくは `src/game/campaign/types.ts` に集約。
2. `migrateV1toV2` を実装し、v1キーからの一度限りの移行 + v2キーへの書き込みを行う。
3. `SaveManager.load/save/clear` をv2ベースに書き換え、v1キーは移行後に削除 (`localStorage.removeItem`) してストレージ肥大を防ぐ。
4. `GameController` 内の `this.currentMissionId`/`this.totalKills`/`this.cleared` という3つのインスタンスフィールドを `SaveDataV2` 1個の保持に統合するか、既存フィールドとの同期方針を決める(推奨: `GameController` は `SaveDataV2` を単一のソースオブトゥルースとして持ち、個別フィールドを廃止)。
5. 既存の単体テスト (あれば) のセーブ関連アサーションをv2形状に更新。

### 受け入れ基準
- v1形式のデータが残っている状態でアプリを起動すると、自動的にv2へ移行され、以後は `multidommander.save.v2` のみが更新される。
- 移行後、`missionId`/`totalKills`/`cleared` の内容が新フィールドに欠損なく反映されている (回帰確認: 移行前後で `cleared` の要素数と `currentMissionId` が一致)。
- 壊れたJSON (手動で不正な文字列をキーに書き込む) を与えても例外を投げず `null` を返し、新規キャンペーンにフォールバックする。
- `version` フィールドが将来 `3` になった場合でも `migrateV1toV2` 相当のチェーン (`migrateV2toV3` を後から追加する形) で拡張できる構造になっている。

### リスク
- `GameController` のフィールドをまとめて `SaveDataV2` 1個に寄せる場合、`onMissionEnd`/`proceed` など既存メソッドの参照箇所すべてを洗い出す必要があり、変更範囲が本Phase中でも一番広い。段階移行 (まずv2型を導入しつつ既存フィールドとの二重持ちを許容し、後続コミットで一本化) を許容してよい。
- 会話シーンの `seenScenes` を入れ忘れると、ブリーフィング前の演出が毎回再生されてテンポを損なう。移行関数のデフォルト値 (`seenScenes: []`) だけでなく、シーン挿入判定側で必ず `seenScenes.includes(sceneId)` を確認する規約をコードレビュー観点として明記する。
