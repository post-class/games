# 05 技術仕様: オーディオと音楽 (Phase 3 音の世界)

本紙は Phase 3「音の世界」の技術仕様。ロードマップ全体の位置づけ・優先順位は `03_ロードマップ.md` を参照。
対象: 動的/適応型BGM、エンジン/アフターバーナー音、空間音響(パン/減衰)、ロックオン・警報系トーン、無線チャッター/VOキューとダッキング、カテゴリ別ミキサー。

## 0. 現状棚卸し

- `src/game/AudioManager.ts:8` が唯一の音響エンジン。`AudioContext` を1つ持ち、`master` という単一 `GainNode` (`AudioManager.ts:31`, gain=0.35) を `destination` に直結するだけの構成。BGM・カテゴリ別ミキサー・空間化は一切ない。
- 合成SEは4種のみ: `gun()` (`AudioManager.ts:92`), `missile()` (`AudioManager.ts:101`), `hit()` (`AudioManager.ts:106`), `explosion()` (`AudioManager.ts:110`)。すべて `tone()`/`noise()` という2つの汎用合成ヘルパー (`AudioManager.ts:53`, `AudioManager.ts:75`) の組み合わせで、位置情報 (`e.position`) を受け取ってはいるが再生には使っていない。
- 有効化は `src/game/bootstrap.ts:42-43` で `new AudioManager(events)` を生成し、`window.addEventListener("keydown", () => audio.enable(), { once: true })` で初回キー入力時に `enable()` (`AudioManager.ts:26`) を呼ぶ一回限りの仕組み。マウス操作や結果画面のクリックでは有効化されないため、キー入力しないユーザーは無音のままになりうる。
- イベント起点は `src/util/EventBus.ts:5-10` の `GameEvents`: `hit`, `destroyed`, `weaponFired{kind}`, `lockAcquired` の4種。ロック**進行度**やロック**解除**、被ロック(自分が狙われている)、シールド危険域、フェーズ遷移などのイベントは存在しない。
- 難易度設定は `src/game/Settings.ts:54` の `SettingsStore` (localStorage key `multidommander.settings.v1`) に難易度のみを保存。音量カテゴリの永続化スキーマは未整備。
- ゲーム進行/フェーズ管理は `src/game/GameController.ts:20` (`Menu → Briefing → Playing → Debrief` 遷移、`GameController.ts:98,120`)。BGMの状態連動はここにフックする以外に自然な場所がない。
- 脅威度算出の材料は `src/game/systems/AISystem.ts` と `src/game/systems/TargetingSystem.ts` にある。`AIController` (`src/game/components/AIController.ts:13`) は `state: AIState` (`Idle/Pursue/Attack/Evade/Form`)、`aggression`、`attackRange`、`target` を持ち、`AISystem.ts:317` の `evaluateTransition` が状態遷移を担う。`Targeting` コンポーネント (`src/game/components.ts:109-114`) は `lockProgress`/`lockTime` を持ち、`TargetingSystem.ts:106-116` でロック角/射程判定を行う。`ThrusterInput.afterburner` (`src/game/components.ts:68`) はプレイヤー/AI共通のスロットル入力で、エンジン音のドライバとして使える。

## 1. 全体アーキテクチャ方針

### 1.1 three.js Audio か 自前 Web Audio か

**判断: 自前 Web Audio (AudioContext + PannerNode) を継続し、three の `AudioListener`/`PositionalAudio` は採用しない。**

理由:
- 現行実装は合成音のみでバッファ資産を持たず、three の `Audio`/`PositionalAudio` が前提とする「デコード済みバッファのロード管理」の恩恵が薄い。
- three の `PositionalAudio` は内部で `PannerNode` をラップするだけで、カテゴリ別ミキサー(Music/SFX/Voice の `GainNode` ツリー)やダッキング制御を独自に組む必要があり、結局 Web Audio ノードを直接触ることになる。二重管理を避ける。
- ただし `AudioListener` の姿勢追従だけは有用なので、**リスナー位置/向きの更新ロジックのみ three 由来の `camera.matrixWorld` から自前で `ctx.listener` (`AudioListener` API または `positionX/orientationX` 系プロパティ) に書き込む**方式を採る。three の `Audio` クラスは使わないが、three の `Camera` から得られる world 変換は活用する。

### 1.2 v2 のノードグラフ

```
AudioContext
 └─ masterGain (Settings.master)
     ├─ musicBus (Settings.music) ── MusicDirector が管理する複数レイヤーの GainNode
     ├─ sfxBus (Settings.sfx)     ── PositionalVoice pool (PannerNode×N) + UI/警報等の非位置音
     └─ voiceBus (Settings.voice) ── VO キュー (直列再生, musicBus をダッキング)
```

- 各カテゴリは `GainNode` 1本 = ミキサーのチャンネルフェーダー。`Settings` の値を `gain.value` に反映する。
- `sfxBus` の配下に「同時発音数を絞るための簡易ボイスプール」を置く(4.4節)。
- `voiceBus` の再生開始/終了で `musicBus` の gain を一時的に下げる(ダッキング、4.5節)。

## 2. 機能別仕様

### 2.1 カテゴリ別ミキサーと Settings 連動

**目的**: Master/Music/SFX/Voice を個別に音量調整できるようにし、ユーザー設定を永続化する。

**現状**: `AudioManager.ts:30-32` はカテゴリの区別がない単一 `master` gain。`Settings.ts` は難易度のみ扱う。

**技術方針**:
- `Settings.ts` の永続化スキーマを拡張する。既存の `SettingsStore.load()/save()` は `Difficulty` 型に固定されているため、破壊的変更を避けて **別キー** `multidommander.settings.audio.v1` に音量設定を分離保存する(既存の難易度データを壊さない)。
- 4値 (`master, music, sfx, voice`: それぞれ 0..1, 既定値 `master=0.8, music=0.6, sfx=0.8, voice=0.9`) を保存。
- `AudioManager` は起動時に `AudioSettingsStore.load()` を読み、4本の `GainNode.gain.value` に反映。設定変更UIからは `AudioManager.setVolume(category, value)` を呼び、即時反映 + 保存。

**タスク分解**:
1. `Settings.ts` に `AudioSettings` 型と `AudioSettingsStore` (load/save, 別キー) を追加。
2. `AudioManager` に4本の `GainNode` を持たせ、`setVolume()` API を追加。
3. `MissionScreens` の設定画面 (`GameController.ts:63` `openSettings()` が呼ぶ画面) にスライダー4本を追加し、`controller` 経由で `AudioManager` に橋渡し。
4. ミュート操作 (`master=0`) 時に `AudioContext.suspend()` は呼ばない (再生キューの時刻管理が狂うため、gainのみで無音化)。

**受け入れ基準**:
- 4カテゴリの音量をそれぞれ独立に 0..1 で変更でき、リロード後も復元される。
- Master=0 でも `AudioContext.state` は `running` を維持し、内部スケジューリング(BGMクロスフェード等)が破綻しない。

**リスク**:
- 既存 `AudioManager.ts:31` の `master.gain.value = 0.35` という決め打ち値をそのまま「既定Master音量」として引き継ぐか、UXレビューで再調整するか要判断。

### 2.2 ブラウザ自動再生ポリシー対応

**目的**: どの操作契機でも確実に `AudioContext` を有効化し、モバイルでも音が出る状態にする。

**現状**: `bootstrap.ts:43` は `keydown` の `once` リスナーのみ。マウス/タッチ操作だけのユーザーは有効化されない。メニュー画面のボタンクリックも拾っていない。

**技術方針**:
- 有効化トリガーを **keydown/pointerdown/click の3種すべて**に広げ、`once` はイベントごとに設定(どれか1つ発火したら残りは自動でリスナー解除)。
- `enable()` (`AudioManager.ts:26`) 内で `new AudioContext()` 直後に `state === "suspended"` なら `resume()` を呼ぶ(iOS Safari はコンストラクタ後も `suspended` のままのケースがある)。
- タイトル画面表示時点(`GameController.ts:36` `showMainMenu()`)で最初のクリック待ちになるため、実質「メインメニューの最初のクリック」で有効化されるのが主経路になる。
- モバイル: タッチ操作は `pointerdown` で拾う。バックグラウンド遷移(タブ非アクティブ)で `AudioContext` がブラウザにより `suspended` にされることがあるため、`visibilitychange` で復帰時に `resume()` を呼ぶ処理を追加。

**タスク分解**:
1. `bootstrap.ts` の有効化リスナーを `["keydown", "pointerdown"]` に拡張。
2. `AudioManager.enable()` に `resume()` フォールバックを追加。
3. `document.addEventListener("visibilitychange", ...)` で復帰時 `resume()`。

**受け入れ基準**:
- キーボードを一度も触らずマウス/タッチのみで最初のメニュー操作をしても音が出る。
- タブを非表示→再表示してもBGM/SEが継続する(コンテキストが `suspended` のまま無音になる回帰がない)。

**リスク**: 一部モバイルブラウザは `resume()` もユーザー操作直後でないと成功しないため、`visibilitychange` 側の `resume()` 呼び出し失敗は握りつぶし、次のユーザー操作時に再試行する設計にする。

### 2.3 動的/適応型BGM (MusicDirector)

**目的**: 平時↔戦闘の激しさに応じてBGMがクロスフェードし、静止画的でない音楽体験を作る。

**現状**: BGMは存在しない。ループ再生・レイヤー管理の仕組みはゼロから構築。

**技術方針(主案): レイヤー(ステム)クロスフェード方式**

- 同一テンポ・同一長さでループする複数ステム(例: `ambient`, `tension`, `combat`, `percussion_top`)を**同時にすべて再生し続け**、`GainNode` の値だけをクロスフェードする。位相が常に揃うため曲間の破綻(ズレ・re-sync)が起きない。CPU/デコードは重いが、Web Audio ではループ音源は軽量。
- 脅威度 `threat: number (0..1)` を1本のスカラーとして `AISystem`/`TargetingSystem` 由来の信号から算出し(2.3.1)、`MusicDirector` がステム別ゲインにマッピングする。
- ループ点はサンプル単位で `AudioBufferSourceNode.loop = true` + `loopStart/loopEnd` を明示指定し、ブラウザのデコード誤差によるクリックノイズを避けるため各ステムの先頭/末尾に数msのフェード(バッファ生成時にオフラインで前処理、またはあらかじめ用意された素材側でゼロクロス処理済みのものを使う)を要求する。

**技術方針(代替案): ジェネレーティブ(合成)方式**

- 現行の `tone()`/`noise()` 路線を拡張し、コード進行やパーカッションパターンをオシレータ/ノイズで都度合成する。
- 比較:

| 観点 | レイヤークロスフェード(主案) | ジェネレーティブ合成(代替) |
|---|---|---|
| 音楽的説得力 | 高い(作編曲されたループ素材) | 低い(合成音楽は単調になりやすい) |
| 実装コスト | 素材制作/選定が必要 | ロジックのみ、素材ゼロ |
| ファイルサイズ | ステムあたり数百KB〜数MB(要圧縮) | 0(コード生成) |
| 遅延/CPU | デコードは初回のみ、再生は軽量 | 都度スケジューリングのオーバーヘッド、質を上げるほど複雑化 |
| ライセンス | CC0/CC-BY 等の配布可能素材を選定必須 | 完全に自作、ライセンス問題なし |

**移行戦略**: P3 初期は**合成SEの技術を流用したプレースホルダBGM**(単純なパッド+ドラム合成、代替案の縮小版)を最初に組み、`MusicDirector` のクロスフェードAPI自体は主案と同じインタフェースで実装する。素材選定(CC0の宇宙戦闘向けループ、例: OpenGameArt/Freesound の CC0 ライセンス曲)が済んだ時点でステムを主案の音源ファイルに差し替える。これにより「脅威度→ゲイン」制御ロジックはSE差し替えの影響を受けない。

**2.3.1 脅威度の算出**

入力ソース:
- `AISystem` 管理下の敵 `AIController.state` (`AIController.ts:15`, `AISystem.ts:317` の `evaluateTransition`)。`Attack` 状態の敵が多いほど激しい。
- `Targeting.lockProgress` (`components.ts:112`, `TargetingSystem.ts:111-112`)。プレイヤーが被ロックされている(=敵の `Targeting.target` がプレイヤー)場合は緊張度を上げる。
- 敵の生存数・プレイヤー `Health.shield/hull` 比率(`components.ts:74-85`)。

```ts
// src/game/audio/MusicDirector.ts (新規)
export interface ThreatInputs {
  attackingEnemies: number;   // AIController.state === "Attack" かつ Faction=Enemy の数
  lockedOnPlayer: number;     // プレイヤーを target にしている敵の lockProgress 合計
  nearbyHostiles: number;     // 一定距離内の敵対機数
  playerShieldRatio: number;  // 0..1, 低いほど危険
}

export function computeThreat(i: ThreatInputs): number {
  const combat = Math.min(1, i.attackingEnemies / 3);
  const lock = Math.min(1, i.lockedOnPlayer);
  const danger = 1 - i.playerShieldRatio;
  return clamp01(0.45 * combat + 0.25 * lock + 0.2 * danger + 0.1 * Math.min(1, i.nearbyHostiles / 5));
}
```

この算出は新規システム `ThreatAssessmentSystem`(固定ステップ、`AISystem`/`TargetingSystem` の後段に追加)が毎ティック計算し、`events.emit("threatLevel", { value })` のような専用イベント、または `MusicDirector` に直接ポーリングさせる(EventBusは離散イベント向けなので、**連続値はポーリング**の方が自然)。`GameController` の `Playing/Briefing/Debrief` フェーズも `MusicDirector.setPhase()` で伝え、戦闘外では脅威度を無視して `ambient` レイヤーのみにする。

**MusicDirector API スケッチ**:

```ts
export type MusicLayer = "ambient" | "tension" | "combat" | "percussion";

export class MusicDirector {
  private layers = new Map<MusicLayer, { gain: GainNode; source: AudioBufferSourceNode }>();
  private currentThreat = 0;

  constructor(private ctx: AudioContext, private bus: GainNode) {}

  /** 4ステムをロードし loop 再生開始 (すべて同時に鳴らし、gain=0 のものは無音)。 */
  async load(buffers: Record<MusicLayer, AudioBuffer>): Promise<void> { /* ... */ }

  /** 毎フレーム(または低頻度, 例10Hz)呼び, 脅威度からレイヤーゲインへ滑らかに追従。 */
  update(threat: number, dt: number): void {
    // 目標ゲインをレイヤーごとに決定し、レートリミット付きで gain.value に近づける
    // (setTargetAtTime を使い、120ms 程度の時定数でクロスフェード)
    const targets = this.targetGains(threat);
    for (const [layer, target] of targets) {
      this.layers.get(layer)?.gain.gain.setTargetAtTime(target, this.ctx.currentTime, 0.6);
    }
  }

  private targetGains(threat: number): Map<MusicLayer, number> {
    return new Map([
      ["ambient", 1 - smoothstep(0.0, 0.5, threat) * 0.6],
      ["tension", smoothstep(0.15, 0.55, threat)],
      ["combat", smoothstep(0.45, 0.8, threat)],
      ["percussion", smoothstep(0.7, 1.0, threat)],
    ]);
  }

  setPhase(phase: "menu" | "briefing" | "playing" | "debrief"): void { /* ambient固定など */ }
}
```

`GainNode.gain.setTargetAtTime(target, time, timeConstant)` を使うことで、脅威度が急変してもクリックノイズなく指数的に追従する(`AudioManager.ts:66-68` で既に使っている `exponentialRampToValueAtTime` より、連続更新には `setTargetAtTime` の方が適する)。

**タスク分解**:
1. CC0ループ素材(または合成プレースホルダ4本)を用意し `public/audio/bgm/*.mp3(or .ogg)` に配置。`fetch + decodeAudioData` でロード。
2. `MusicDirector` クラス実装 (load/update/setPhase)。
3. `ThreatAssessmentSystem` を追加し `scheduler.addFixed` に登録 (`bootstrap.ts:52-62` 付近)、`GameController` のフェーズ遷移箇所 (`GameController.ts:98`, `GameController.ts:120` 等) で `setPhase()` 呼び出しを追加。
4. `GameController` にBGM開始/停止のタイミング(タイトル表示時にロード開始、`enable()` 後に再生開始)を実装。

**受け入れ基準**:
- 敵Attack数が増えるとBGMが combat レイヤーへ聴感上明確にクロスフェードし、離脱すると数秒でambientに戻る。
- レイヤー切り替え時にポップ/クリックノイズが聴こえない。
- ブリーフィング/デブリーフ中はambient/tensionのみで、パーカッションが鳴らない。

**リスク**:
- 4ステム同時デコード+再生はモバイルでメモリ/CPU負荷が増える。ステム数を2(ambient+combat)に削減するフォールバックを低スペック向けに用意する。
- 素材のライセンス確認(CC0/CC-BY表記の同梱)を怠るとリリースブロッカーになる。

### 2.4 エンジンループ音・アフターバーナー

**目的**: スロットル操作に応じて連続的に変化するエンジン音、アフターバーナー使用時の噴射音を追加し、操縦の触覚フィードバックを強化する。

**現状**: エンジン音は皆無。`ThrusterInput.linear.z`(スロットル, `components.ts:65`)と `ThrusterInput.afterburner`(`components.ts:68`)は物理系 (`FlightModelSystem.ts:62-66`)でのみ使われ、音には未接続。

**技術方針**:
- ループ再生する2つの `AudioBufferSourceNode`(`engineHum`: 低速アイドル〜巡航ノイズ、`afterburnerRoar`: AB専用の広帯域ノイズ)を常時再生し、gainとfilterでスロットルに追従させる。**都度生成/破棄ではなく常時ループ+ゲイン制御**にすることで、`start/stop` の呼び出しコストとクリックノイズを避ける。
- 合成継続方針: 現行の `noise()` (`AudioManager.ts:75`)と同種の手法で、`BiquadFilterNode`(lowpass, `frequency` をスロットルに応じて300Hz〜1200Hzでスイープ)+ `GainNode` を使う。専用の長尺ノイズバッファ(数秒、シームレスループ用にゼロクロスさせた `noiseBuffer` 拡張版)を用意する。
- プレイヤー機のみエンジン音を鳴らす(非位置, リスナー直結)。AI機のエンジン音は空間音響(2.5節)の一部として距離減衰込みで小さく鳴らす(近距離のドッグファイトでの存在感のため)。

```ts
// AudioManager v2 内、エンジン専用モジュール
class EngineVoice {
  private humGain!: GainNode;
  private humFilter!: BiquadFilterNode; // lowpass, hum ソースの手前に直列
  private abGain!: GainNode;            // afterburner ノイズソースの手前

  /** 毎フレーム呼び、throttle(0..1)/afterburner(bool) を反映。 */
  update(throttle: number, afterburnerOn: boolean): void {
    const t = this.ctx.currentTime;
    this.humGain.gain.setTargetAtTime(0.08 + throttle * 0.22, t, 0.08);
    this.humFilter.frequency.setTargetAtTime(300 + throttle * 900, t, 0.08);
    this.abGain.gain.setTargetAtTime(afterburnerOn ? 0.35 : 0.0, t, afterburnerOn ? 0.05 : 0.25);
  }
}
```

- 更新契機: `HudSystem`と同じ可変ステップ側 (`bootstrap.ts:66-70` の `addVariable` グループ)に `EngineAudioSystem` を追加し、プレイヤーの `ThrusterInput` を毎フレーム読んで `EngineVoice.update()` を呼ぶ。固定ステップでなく可変ステップで十分(音のパラメータ変化は聴覚的に粗くても違和感がない)。

**受け入れ基準**:
- スロットルを上げ下げすると聴感上遅延なく(数十ms以内)エンジン音のピッチ/音量が追従する。
- アフターバーナーON/OFFがクリックノイズなく滑らかにフェードする。
- ブリーフィング/デブリーフ中(`shouldRunFixed` が false, `bootstrap.ts:34`)はエンジン音を止める。

**リスク**: 常時ループ音源はモバイルの電池/CPUに影響するため、タブ非表示中(`visibilitychange`)はエンジン音のgainを0にする配慮が必要。

### 2.5 空間音響 (PannerNode による定位)

**目的**: 敵の砲撃/被弾/爆発が、画面内のどこで起きたかを音の方向・距離感で伝える。

**現状**: `weaponFired`/`hit`/`destroyed` イベント(`EventBus.ts:6-8`)は `position: Vector3` を運んでいるが、`AudioManager.ts:16-18` はそれを一切使わず全SEをリスナー直結で鳴らしている。

**技術方針**:
- 自前 `PannerNode`(`panningModel: "HRTF"`, `distanceModel: "inverse"`, `refDistance`/`maxDistance` をゲームスケールに合わせて調整、例 `refDistance=50, maxDistance=3000, rolloffFactor=1`)を SE 経路に挿入する。three の `PositionalAudio` は使わない(1.1節の判断)。
- リスナー姿勢は `CameraRig`(`bootstrap.ts:68` で `addVariable` 登録)が更新する `render.camera` の world 変換から、可変ステップの音響更新タイミングで `ctx.listener.positionX.value` 等(または `setPosition`/`setOrientation` の非推奨APIではなく `AudioListener` のプロパティ経由)にコピーする。
- 発音関数を「位置あり/位置なし」で分離する:

```ts
interface PositionalPlayOptions { position: Vector3; refDistance?: number }

class AudioManager {
  // tone()/noise() の接続先を panner 経由に変える版。位置なしSEは直接 sfxBus へ。
  private playPositional(build: (dest: AudioNode) => void, opts: PositionalPlayOptions): void {
    if (!this.ctx) return;
    const panner = this.ctx.createPanner();
    panner.panningModel = "HRTF";
    panner.distanceModel = "inverse";
    panner.refDistance = opts.refDistance ?? 50;
    panner.maxDistance = 3000;
    panner.positionX.value = opts.position.x;
    panner.positionY.value = opts.position.y;
    panner.positionZ.value = opts.position.z;
    panner.connect(this.sfxBus);
    build(panner);
  }

  // camera の world 変換 (position/quaternion) を ctx.listener の position*/forward*/up* に反映。
  private updateListener(camera: Camera): void { /* ... */ }
}
```

- `tone()`/`noise()` (`AudioManager.ts:53,75`)を、接続先ノードを引数化(現在ハードコードされた `this.master` 接続を `destination: AudioNode` パラメータに変更)してリファクタし、位置ありSEは `panner` に、位置なしSE(UI, 警報)は `sfxBus` に直結する。
- 減衰カーブがゲームの戦闘距離感(数十〜数百m〜数km)に対して適切か、`refDistance`/`maxDistance` はプレイテストで調整する前提の初期値として上記を置く。

**タスク分解**:
1. `tone()`/`noise()` を `destination` パラメータ化。
2. `PannerNode` 生成ヘルパー `playPositional()` を実装、`gun/missile/hit/explosion` を位置あり版に変更(`weaponFired.position`, `hit.position`, `destroyed.position` を使用)。
3. リスナー更新を可変ステップ系に追加 (`bootstrap.ts:66-70` 付近、`CameraRig` の後)。
4. 自機由来の発射音(`shooter` がプレイヤー自身の場合)は距離ゼロに近いため、位置なし(直接 `sfxBus`)の特別扱いにするか検証。

**受け入れ基準**:
- 左右のスピーカー/ヘッドフォンで、右側にいる敵の発砲音が右から聞こえる。
- 自機の発砲音は常に明瞭(位置減衰で埋没しない)。
- 同時に多数の爆発が起きても極端な音割れがない(2.6節のミキシング制御と連動)。

**リスク**: `PannerNode` の `HRTF` モデルはCPUコストが非HRTF(`equalpower`)より高い。同時発音数が多い場面(4.4節のプール上限)で負荷を見て `panningModel` を `equalpower` にフォールバックする設定を用意する。

### 2.6 ロックオン/被ロック(ミサイル警告)トーン・低シールド警報

**目的**: プレイヤーが「ロックされている」「シールドが危険」という状態をSEで即座に把握できるようにする。

**現状**: `lockAcquired` イベント(`EventBus.ts:9`)は定義済みだが `AudioManager` は購読していない。ロック**進行**は `Targeting.lockProgress`(`components.ts:112`)としてポーリング可能な値のみで存在し、離散イベントがない。シールド関連イベントは存在しない。

**技術方針**:
- **新規イベントを EventBus に追加**する(`EventBus.ts:5-10` の `GameEvents` を拡張):
  - `lockedByEnemy: { by: EntityId; progress: number }` — プレイヤーが被ロックされている進行度。`TargetingSystem` が敵側の `Targeting` を評価する際、target がプレイヤーの場合に emit。閾値到達型(`missileWarning: { by: EntityId }`, `progress >= 1` で一度だけ)も分ける。
  - `shieldCritical: { entity: EntityId; ratio: number }` — `DamageSystem` 側で shield/shieldMax が閾値(例0.25)を下回った/上回った(解除)タイミングで emit。
- 被ロック警告音: 周期的なビープ(`tone("square", ...)` の短パルスをsetIntervalではなく `AudioContext` の時刻ベースでスケジューリングし、`lockProgress` が上がるほどビープ間隔を短くする「ミサイルロック警報」の定番表現)。ロック完了で連続トーンに切り替え。
- 低シールド警報: 低周波の警告音(トライアド的な不協和トーンの短い繰り返し)をシールド危険域の間だけループさせ、回復で停止。`sfxBus` 直結(位置なし、UI的な警報のため)。
- どちらも「継続する警報」なので、SEの単発再生モデル(`tone()`)ではなく **状態を持つ `AlarmVoice`** として実装し、`setActive(on, intervalMs)` で `AudioContext.currentTime` ベースの周期スケジューリングを開始/停止する(`setInterval`ではなくオーディオクロックに揃えることでドリフトを避ける)。ロック警報は `intervalMs` を `lockProgress` に応じて短縮する。

**タスク分解**:
1. `GameEvents` に `lockedByEnemy`, `missileWarning`, `shieldCritical` を追加。
2. `TargetingSystem` (`TargetingSystem.ts:78`) にプレイヤー被ロック検出を追加(敵側の `Targeting.target === playerEntity` を走査)。
3. `DamageSystem` にシールド閾値クロス検出を追加(ヒステリシス付き、チャタリング防止)。
4. `AudioManager` に `AlarmVoice` を2系統(ロック警報/シールド警報)実装し、上記イベントで `setActive()`。

**受け入れ基準**:
- 敵に照準を合わせられ続けるとビープが加速し、ロック完了で連続音になる。ロックが外れると即停止。
- シールドが閾値を割ると警報が鳴り、回復すると自然に停止する(頻繁なON/OFF点滅がない)。

**リスク**: 複数の敵から同時ロックされた場合の多重化(最も進行度が高いロックのみ音にする、等の集約ルールが必要)。

### 2.7 無線チャッター/ボイス(VO)キューとBGMダッキング

**目的**: 僚機/管制からの短い音声(ミッション開始、敵発見、被害報告等)を無線ノイズ演出付きで再生し、その間BGM/SFXの聴感上の見通しを確保する。

**現状**: VOは存在しない。テキストの無線的な演出は `InputSystem.ts` 経由で `mission.announce(text, ...)` (`bootstrap.ts:53`) としてテキストのみ実装されている(音声化は未着手)。

**技術方針**:
- VOは**直列再生キュー**(同時に2つ以上喋らせない)。`voiceBus` に接続する `VoiceQueue` を実装し、`enqueue(clip, priority)` で追加、再生中に高優先度が来たら現行をフェードアウトして差し替え。
- 無線らしさは `BiquadFilterNode`(bandpass, 300Hz-3000Hz)+ 軽いビットクラッシュ的な歪み(`WaveShaperNode`)をVO再生経路に直列挿入して演出する(素材そのものを加工するのではなく再生時にリアルタイムでフィルタをかけることで、素材を汎用のまま使い回せる)。
- **ダッキング**: VO再生開始時に `musicBus`(および `sfxBus` の一部)のgainを `setTargetAtTime` で一時的に下げ(例: 70%減、時定数0.15秒)、VO終了で戻す。`MusicDirector.update()` が出す目標値に対して「ダッキング係数」を掛け算する形で二重制御を避ける。

```ts
class VoiceQueue {
  private queue: Array<{ buffer: AudioBuffer; priority: number }> = [];
  private playing = false;

  enqueue(buffer: AudioBuffer, priority = 0): void {
    this.queue.push({ buffer, priority });
    this.queue.sort((a, b) => b.priority - a.priority);
    if (!this.playing) this.playNext();
  }

  /** キューから1件取り出し radioFilter 経由で voiceBus に再生。空になったら duck(false)。 */
  private playNext(): void { /* createBufferSource → connect(radioFilter).connect(voiceBus) → onended で再帰 */ }

  private duck(on: boolean): void {
    this.musicBus.gain.setTargetAtTime(on ? this.musicBaseline * 0.3 : this.musicBaseline, this.ctx.currentTime, 0.15);
  }
}
```

- 素材: 短いVOクリップ(数十〜数百ファイル規模になりうる)は容量が嵩むため、P3スコープでは**テキストベースの無線チャッター(既存 `mission.announce`)をそのまま活用し、VOは効果音的な「無線ビープ/静的ノイズの短いスタブ」程度に留める**代替案も明記する。フルVOの導入(ローカライズ含む)はP3の主スコープ外とし、以後のフェーズ(コンテンツ拡充フェーズ)での素材investmentと連動させる判断を推奨。

**タスク分解**:
1. `VoiceQueue` 実装(優先度付きキュー、ダッキング連動)。
2. 無線フィルタ(bandpass+歪み)チェーンの実装。
3. `MissionSystem`/`MissionManager` 側のテキスト通知箇所(`bootstrap.ts:53` の `announce` 呼び出し等)にVOトリガーのフック点を用意(実際の音声素材は本紙スコープ外、フック配線のみ)。

**受け入れ基準**:
- VO再生中はBGMが明確に(だが不自然に無音化しない程度に)引くこと。
- 複数VOが同時に来ても重ならず、優先度の高い方が先に再生される。

**リスク**: VO素材のライセンス/ローカライズ体制が未整備。P3では配線とダッキング機構の実装に留め、素材投入は後続タスクに切り出す。

### 2.8 ミキシング全体制御(同時発音数/ポリフォニー管理)

**目的**: 爆発多数発生時や乱戦時に音が割れたり、ノード数が無制限に増えてパフォーマンスが劣化しないようにする。

**現状**: `AudioManager.ts` はSEごとに都度 `createOscillator`/`createBufferSource` を生成し `start/stop` するだけで、上限管理がない。現状の発音数(4種類、間引きは `gun()` の `lastGunAt` (`AudioManager.ts:13,96`) のみ)では問題化していないが、SE種類が増えると顕在化する。

**技術方針**:
- カテゴリごとに**同時発音数の上限**を設ける(例: `explosion` 系は同時4つまで、超過分は最も古い/最も遠いものを打ち切るか、そもそも新規発音をスキップ)。
- 実装は「アクティブノードのリスト管理」ではなく、**イベント発生時刻のスロットリング**(`gun()` の手法を一般化)と**カテゴリ別カウンタ**(発音開始時+1、`onended`で-1)の併用。
- `sfxBus` 全体にリミッター的な `DynamicsCompressorNode` を1つ挿入し、突発的な多重爆発でもクリップしないようにする(`sfxBus -> compressor -> masterGain` の順)。

```ts
const compressor = ctx.createDynamicsCompressor();
compressor.threshold.value = -18;
compressor.ratio.value = 6;
sfxBus.connect(compressor).connect(masterGain);
```

**タスク分解**:
1. `sfxBus` 出力に `DynamicsCompressorNode` を追加。
2. SE種別ごとの同時発音カウンタ(`Map<SfxKind, number>`)を `AudioManager` に持たせ、上限超過時は発音を抑制する `tryPlay(kind, fn)` ラッパーを用意。
3. `explosion`/`hit` のような多発イベントを優先してカウンタ対象にする(`gun`は既存の時間間引きで十分)。

**受け入れ基準**:
- 10機以上が同時に爆発するような場面でも音が破綻(デジタルクリップ/ノード数の異常増加によるフレーム落ち)しない。
- 通常戦闘時の聴感には変化がない(圧縮が過剰にかからない設定値であること)。

**リスク**: コンプレッサーの設定値はプレイテストでの微調整が前提。厳しすぎるとダイナミクスが失われ迫力が減る。

## 4. 段階導入の順序(P3内部の依存関係)

1. カテゴリ別ミキサー配線 + 自動再生対応の強化(2.1, 2.2) — 他機能の土台。
