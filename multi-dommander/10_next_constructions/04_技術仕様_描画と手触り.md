# 04 技術仕様: 描画と手触り (Phase 1 見た目の革命 / Phase 2 戦闘の手触り)

本紙は Phase 1「見た目の革命」と Phase 2「戦闘の手触り(ジュース)」の技術仕様。ロードマップ全体の位置づけ・優先順位は `03_ロードマップ.md` を参照。P0 基盤(プール付きVFXマネージャ・イベント拡張・性能計測)は前提として存在するものとし、本紙はその上に乗る機能を定義する。

## 0. 現状棚卸し

- レンダリングは `src/game/Game.ts:67` の `this.render.renderer.render(this.render.scene, this.render.camera)` 一発のみ。ポストプロセスの挿入点はここ一箇所であり、`EffectComposer.render()` に置き換えるだけで済む構造。
- シーン初期化は `src/render/SceneSetup.ts:20` の `setupScene()`。`WebGLRenderer` は `src/render/SceneSetup.ts:33` で `{ antialias: true, powerPreference: "high-performance" }` のみ指定され、`toneMapping`/`outputColorSpace` は既定値(`NoToneMapping`)のまま。背景は `Color(0x01030a)` 単色 (`SceneSetup.ts:22`)、fog は `Fog(0x01030a, 4000, 12000)` (`SceneSetup.ts:23`)。ライトは `DirectionalLight` 主光源+リムライト+`AmbientLight` の3灯 (`SceneSetup.ts:39-45`)、環境マップは無し。`onResize` (`SceneSetup.ts:51`) はカメラアスペクトとレンダラーサイズのみ更新するため、Composer導入時はここに解像度リサイズを追加する必要がある。
- 星空は `src/render/SkyboxStars.ts:7` の `createStarfield()` が `Points` 8000個を半径15000の球殻上にランダム分布させるのみ。星雲・惑星・太陽は皆無。
- マテリアルは `src/render/MeshFactory.ts:39-52` で `MeshStandardMaterial`(`metalness`/`roughness`固定値、`flatShading: true`)。環境マップ(`envMap`)が無いため金属面の反射がフラットで安っぽく見える。
- 爆発は `src/game/systems/ExplosionSystem.ts:27` の `ExplosionSystem` が単一責務: `events.on("destroyed", ...)` / `events.on("hit", ...)` (`ExplosionSystem.ts:35-36`) を購読し、`SphereGeometry(1,12,12)` 1個をイージング拡大+フェードするだけ (`ExplosionSystem.ts:74-77`)。閃光・衝撃波・デブリ・煙・火花のレイヤー分離は無い。マテリアルは `spawn()` ごとに `new MeshBasicMaterial(...)` (`ExplosionSystem.ts:40`) を生成し `dispose()` (`ExplosionSystem.ts:58,70`) するが、ジオメトリだけ共有(`explosionGeo`, `ExplosionSystem.ts:21`)でマテリアルはプールされていない。
- イベントは `src/util/EventBus.ts:5-10` の4種のみ: `hit{target,source,damage,position}`, `destroyed{entity,position,faction}`, `weaponFired{shooter,position,kind:"gun"|"missile"}`, `lockAcquired{shooter,target}`。発火元は `src/game/systems/DamageSystem.ts:64`(destroyed)、`src/game/systems/CollisionSystem.ts:110`(hit)、`src/game/systems/WeaponSystem.ts:78,102`(weaponFired、`t.position.clone()`=機体中心。マズル座標 `muzzleWorld` はローカル変数のままイベントに載っていない)。マズルフラッシュの正確な発生点にはハードポイント座標の追加が必要。
- マズル/弾/ミサイル/ナビマーカーのメッシュ生成は `src/render/MeshFactory.ts` に集約。`createProjectileMesh` (`MeshFactory.ts:100`)、`createMissileMesh` (`MeshFactory.ts:176`)、機体の `engineGlow` (`MeshFactory.ts:83-94`, `MeshBasicMaterial`+`AdditiveBlending`) が既存の発光表現パターン。トレイル・プルーム・マズルフラッシュはこの延長線に実装するのが自然。
- カメラは `src/render/CameraRig.ts:17` の `CameraRig`。`stiffness`(既定6, `CameraRig.ts:25`)による単純 `lerp` (`CameraRig.ts:42`) と `lookAt` (`CameraRig.ts:47`)のみ。シェイク/FOVキック/ヒットストップの状態を保持する場所が無い。`src/game/bootstrap.ts:68` で `new CameraRig(render.camera, getPlayer)` としてスケジューラの可変系に登録。
- HUDは `src/hud/HudView.ts:66` の `HudView` が DOM/CSS ベースで一括管理。ヒットマーカー/キルフィード/被弾ビネットの要素は無い。既存の `el()` ヘルパー (`HudView.ts:326`) と `hud.css` のクラス命名規則(`hud-xxx`, `HudView.ts:88-101` 参照)に倣って追加する。
- パフォーマンス制約: `src/config/physicsConfig.ts:4` で `fixedDt: 1/60`。60fps 前提の固定ステップ物理と可変レート描画の分離構造 (`Game.ts:51-66`) を崩さないこと。

## 1. 全体アーキテクチャ方針

### 1.1 描画パイプラインの拡張方式

**判断: `Game.ts` のレンダリング呼び出しを `EffectComposer` に一本化し、`RenderContext` にコンポーザとVFXマネージャを追加する。**

理由:
- `Game.frame()` (`Game.ts:45`) は物理→描画の1回のループで完結しており、`renderer.render()` を `composer.render(dt)` に差し替えるだけで既存の固定ステップ構造に影響しない。
- `RenderContext` (`SceneSetup.ts:12-17`) はシーン/カメラ/レンダラー/破棄関数のみの薄いインタフェースなので、`composer: EffectComposer` と `vfx: VfxManager` を追加しても呼び出し側 (`bootstrap.ts`) の変更は最小限。

```ts
// src/render/SceneSetup.ts (拡張後の型)
export interface RenderContext {
  scene: Scene;
  camera: PerspectiveCamera;
  renderer: WebGLRenderer;
  composer: EffectComposer;
  bloomPass: UnrealBloomPass;
  dispose(): void;
}
```

```ts
// src/game/Game.ts:67 の置き換え
this.render.composer.render(); // EffectComposer が内部で RenderPass→BloomPass→AA→Grading を直列実行
```

### 1.2 VFXイベントの分類とプール付きVFXマネージャ

P0基盤で用意される「プール付きVFXマネージャ・イベント拡張」に対して、本紙の機能が要求する具体的なイベント/APIを定義する。

**イベント拡張 (`EventBus.ts:5` の `GameEvents` に追加)**:

```ts
export interface GameEvents {
  hit: { target: EntityId; source: EntityId; damage: number; position: Vector3 };
  destroyed: { entity: EntityId; position: Vector3; faction: number; velocity: Vector3 };
  weaponFired: {
    shooter: EntityId;
    position: Vector3;      // 機体中心 (既存互換)
    muzzlePosition: Vector3; // ハードポイント実座標 (新規、マズルフラッシュ用)
    direction: Vector3;      // 発射方向 (新規、フラッシュ/トレイル向き用)
    kind: "gun" | "missile";
  };
  lockAcquired: { shooter: EntityId; target: EntityId };
  shieldHit: { entity: EntityId; position: Vector3; normal: Vector3 }; // 新規: シールドリップル用
  cameraShake: { intensity: number; duration: number };                // 新規: 被弾/被撃墜フィードバック用
}
```
- `weaponFired` への `muzzlePosition`/`direction` 追加は `WeaponSystem.ts:78-82` と `:102-106` の `emit` 呼び出しに1行追加するだけで済む(`muzzleWorld` は既にローカル変数として計算済み、`WeaponSystem.ts:64`)。
- `shieldHit` は `CollisionSystem.ts:110` の `hit` emit 箇所で、命中エンティティに `Shield` コンポーネントかつ `shieldHp>0` の場合に追加発火する。

**プール付きVFXマネージャの型スケッチ**(P0基盤が提供する想定インタフェース、本紙の各機能はこれに依存):

```ts
// src/render/VfxManager.ts (想定)
interface PooledParticleSystem<T> {
  spawn(config: T): void;
  update(dt: number): void;
  dispose(): void;
}

export class VfxManager {
  private readonly pools = new Map<string, PooledParticleSystem<unknown>>();
  register<T>(key: string, pool: PooledParticleSystem<T>): void;
  spawn<T>(key: string, config: T): void; // プールから再利用、上限超過時は最古を回収
  update(dt: number): void;               // Game.frame() から可変レートで一括更新
  activeCount(): number;                  // 性能計測用
}
```
- 各エフェクト種別(爆発閃光/衝撃波/デブリ/煙/火花/マズルフラッシュ/トレイル/プルーム/シールドリップル)は `InstancedMesh` または `Points` ベースの固定長プールとして `pools` に登録し、`new Mesh`/`new Material` を毎フレーム生成しない(GC回避、性能予算は3節で規定)。

## 2. Phase 1: 見た目の革命

### 2.1 ポストプロセス パイプライン (Bloom / AA / トーンマッピング / カラーグレード)

**目的**: 発光体(エンジングロー・弾・爆発)に自然なブルームを付け、ジャギーを抑え、フィルムライクな階調にして画面全体の質を一段上げる。

**現状**: `Game.ts:67` は `renderer.render()` の素通し。`renderer.antialias: true` (`SceneSetup.ts:33`) のMSAAのみで、ポスト処理・トーンマッピングは無し。既に `AdditiveBlending` の発光マテリアルが多数存在 (`MeshFactory.ts:83-89`, `:100-107`) するため、Bloom導入の効果は大きい。

**技術方針**:
- `EffectComposer` を `SceneSetup.setupScene()` 内で構築し、`RenderContext` に含める。パス構成:
  1. `RenderPass(scene, camera)`
  2. `UnrealBloomPass(new Vector2(w,h), strength=0.9, radius=0.55, threshold=0.82)` — 閾値を高めに取り `AdditiveBlending` の発光メッシュのみ光らせ、通常マテリアルの白飛びを避ける。
  3. `SMAAPass(w*pixelRatio, h*pixelRatio)` — MSAA非対応のポストプロセス後段でのエイリアシング対策。`renderer.antialias` は Composer導入後は不要になるため `false` に変更し、SMAAに一本化してGPU負荷を抑える。モバイルGPU(タイル型レンダラ)では `FXAAPass` にフォールバック可能なスイッチを設ける(3.1節)。
  4. 自作 `ShaderPass`(ビネット+カラーグレード) — 画面端減光とコントラスト/彩度カーブを1パスのフラグメントシェーダで実装。被弾ビネット(2.4節、HUD側)とは別レイヤーで、常時薄くかける環境ムード用。
- `renderer.toneMapping = ACESFilmicToneMapping; renderer.toneMappingExposure = 1.0;`(`SceneSetup.ts:33` 直後に追加)、`renderer.outputColorSpace = SRGBColorSpace` を明示。ACES化により `AmbientLight(0x223344, 1.0)` (`SceneSetup.ts:45`) や `DirectionalLight` の見え方が変わるため、光量の再調整が必要(タスク分解に明記)。
- `onResize` (`SceneSetup.ts:51-56`) に `composer.setSize(w,h)` と `bloomPass.resolution.set(w,h)` を追加。

```ts
// src/render/SceneSetup.ts 拡張スケッチ
const composer = new EffectComposer(renderer);
composer.addPass(new RenderPass(scene, camera));
const bloomPass = new UnrealBloomPass(
  new Vector2(window.innerWidth, window.innerHeight), 0.9, 0.55, 0.82,
);
composer.addPass(bloomPass);
composer.addPass(new SMAAPass(window.innerWidth * renderer.getPixelRatio(), window.innerHeight * renderer.getPixelRatio()));
const gradePass = new ShaderPass(VignetteGradeShader);
gradePass.renderToScreen = true;
composer.addPass(gradePass);
renderer.toneMapping = ACESFilmicToneMapping;
```

**タスク分解**:
1. `SceneSetup.ts` に `EffectComposer`/`RenderPass`/`UnrealBloomPass`/`SMAAPass`/`ShaderPass` を導入し `RenderContext` を拡張。
2. `Game.ts:67` を `composer.render()` に置換。
3. `ACESFilmicToneMapping` 導入に伴う `DirectionalLight` 強度 (`SceneSetup.ts:39,42`) と `AmbientLight` 強度 (`SceneSetup.ts:45`) の再調整パス(ビジュアルレビューで数値決定)。
4. 自作ビネット/カラーグレード `ShaderPass` のGLSL実装(既存の被弾ビネット3.4節とは別物、常時適用の弱いムード効果)。
5. `onResize` にComposer/BloomPassのリサイズ処理追加。
6. モバイル/低性能GPU向けに `SMAAPass → FXAAPass` へ切替可能な設定フラグを用意(3.1節の性能予算参照)。

**受け入れ基準**:
- エンジングロー・曳光弾・爆発閃光が周囲に自然な光の滲みを持ち、閾値以下の通常マテリアルは滲まない。
- 画面端から中央にかけての階調がACES化前より映画的(暗部が締まり、ハイライトが破綻しない)。
- リサイズ時にBloom/SMAAの解像度もカメラ同様に追従する(ぼやけ/エイリアシング残存が無い)。

**リスク**:
- `ACESFilmicToneMapping` は既存の色決め打ち値(`p.bodyColor`/`p.accentColor` 等 `ShipDefinition`)の見た目を変えるため、既存機体のカラーバランスの再確認が必要。
- `UnrealBloomPass` はGPU負荷が比較的高い(複数解像度のブラー)。3.1節の性能予算で強度/解像度を可変にする。

### 2.2 星空刷新 + 星雲 + 惑星/太陽遠景

**目的**: `Points` 8000個の単調な星空(`SkyboxStars.ts:7`)を、奥行きと個性のある宇宙背景に拡張する。

**現状**: `createStarfield()` (`SkyboxStars.ts:7-53`) は球面一様分布+HSLゆらぎの `PointsMaterial`(`size:40`, `sizeAttenuation:true`, `SkyboxStars.ts:40-46`)のみ。`scene.background` は単色 `Color(0x01030a)` (`SceneSetup.ts:22`)。星雲/惑星/太陽は皆無で、`fog` (`SceneSetup.ts:23`, near=4000/far=12000)が遠景を単純にフェードするだけ。

**技術方針**:
- **星空自体の改善**: 既存 `Points` は維持しつつ、`PointsMaterial` に `map`(円形グラデーションのスプライトテクスチャ、`CanvasTexture` で動的生成し `THREE.AdditiveBlending` に変更)を追加して星が単純な正方形ドットに見える現状(`sizeAttenuation`のみでは角ばる)を改善。2層目として遠距離・低密度の暗めの星群を別 `Points`(`radius`を2倍程度)で重ね、パララックス感を出す。
- **星雲**: 大型の半透明 `Sprite` または `PlaneGeometry` +カスタム `ShaderMaterial`(フラクタルノイズ的なグラデーション、`AdditiveBlending`, `depthWrite:false`)を数枚、`SkyboxStars.ts` に `createNebulae()` として追加。`frustumCulled = false`(既存 `starfield`/`navMarker` と同じパターン、`SkyboxStars.ts:51`, `MeshFactory.ts:171`)で常時描画。
- **惑星/太陽**: `SphereGeometry` + `MeshBasicMaterial`(太陽は自己発光、`emissive`+Bloom閾値超えで滲ませる)/`MeshStandardMaterial`(惑星は主光源で片面照射され「球体である」実感を出す)を遠景に数個配置。カメラからの視差がほぼ無い超遠距離(`fog.far=12000` の外、例: 半径20000〜40000)に固定し、`frustumCulled=false` で常時レンダリング対象にする。
- 実装は `SkyboxStars.ts` に関数を追加する形で既存の1ファイル構成を維持(`createStarfield`と並列に `createNebulae`, `createDistantPlanets`をexport)、`SceneSetup.ts:48` の `scene.add(stars)` の並びに追加する。

```ts
// src/render/SkyboxStars.ts 追加スケッチ
export function createNebulae(count = 4, radius = 18000): Group { /* Sprite×N, AdditiveBlending */ }
export function createDistantPlanets(defs: PlanetDef[]): Group { /* SphereGeometry + Standard/Basic */ }
interface PlanetDef { radius: number; distance: number; color: number; emissive?: number; }
```

**タスク分解**:
1. 星スプライトテクスチャを `CanvasTexture` で生成する小関数を追加し `PointsMaterial.map` に設定(円形ソフトグロー、ジャギー星を解消)。
2. 遠距離パララックス層(2層目 `Points`)を追加。
3. `createNebulae()`: `Sprite`+グラデーションテクスチャ(またはノイズ`ShaderMaterial`)を3〜5枚、色は青紫/オレンジ系のバリエーション。
4. `createDistantPlanets()`: 惑星2〜3個+太陽1個を配置。太陽はBloom閾値(2.1節 `threshold=0.82`)を超える輝度に設定し光滲みで存在感を出す。
5. `SceneSetup.ts` に呼び出しを追加し、`scene.fog` の range を惑星/星雲配置後に再調整(遠景がfogで消えすぎないよう `fog.far` を惑星距離より遠くに設定、または惑星群を `fog` の影響を受けない `Layers` 分離を検討)。

**受け入れ基準**:
- 星が円形の柔らかい光点に見え、遠近2層でパララックスが感じられる。
- 星雲が画面の一部の方向に色付いた大気感を出し、単色背景の単調さが解消される。
- 太陽/惑星が遠景に固定的に存在し、機動しても極端な視差でちらつかない(超遠距離配置+`frustumCulled=false`で安定)。
- 追加要素が `fog` によって不自然に消えない(遠景オブジェクトの視認性を優先しfog設定を調整済み)。

**リスク**:
- 星雲を`ShaderMaterial`のノイズ生成にする場合、モバイルGPUでのフラグメントシェーダ負荷に注意(3.1節)。テクスチャベース(事前生成PNG的なCanvasグラデーション)の方が安全な代替。
- 惑星の`MeshStandardMaterial`はPMREM環境マップ導入(2.3節)後、遠景オブジェクトが環境マップの影響を受けて意図しない反射をする可能性があり、`envMapIntensity`個別調整が必要になる場合がある。

### 2.3 環境マップ (PMREMGenerator / RoomEnvironment) によるマテリアル質感向上

**目的**: `MeshStandardMaterial`(`metalness:0.6, roughness:0.45`, `MeshFactory.ts:39-44`)の金属機体が、環境マップ無しでフラットに見える現状を解消し、反射のある質感にする。

**現状**: `MeshFactory.ts` の機体マテリアルは `metalness`/`roughness` のみ指定、`envMap` 未設定。PBRの`metalness`が高い設定(0.6)ほど環境マップ無しでは黒く沈みやすく、現状の見た目の「安っぽさ」の主因の一つ。

**技術方針**:
- `SceneSetup.setupScene()` 内で `PMREMGenerator` を使い、`RoomEnvironment`(three.js標準の`examples/jsm/environments/RoomEnvironment.js`、スタジオ的な明暗のある部屋を事前レンダリングしたIBL用テクスチャ)から `scene.environment` を1回生成する。宇宙空間の見た目とは直接一致しないが、金属面に「周囲に何かがある」自然な反射を与える最も低コストな手段(実写HDRIの追加ロードが不要)。
- `renderer.render()` 一発ではなく `pmremGenerator.fromScene(new RoomEnvironment(), 0.04)` を起動時に一度だけ実行し、生成した `RenderTarget.texture` を `scene.environment` に代入。`pmremGenerator.dispose()` を忘れずに呼ぶ(生成用シーンは使い捨て)。
- `scene.background` は既存の `Color(0x01030a)` (`SceneSetup.ts:22`) のまま維持し、`scene.environment` のみ反射用に分離設定する(`background`と`environment`は別プロパティ、three.js r170で両立可能)。
- 機体マテリアル側 (`MeshFactory.ts:39-52`) は変更不要(`envMap`を明示せず`scene.environment`のグローバル環境マップが自動適用される、three.jsのデフォルト挙動)。ただし `envMapIntensity` を `MeshStandardMaterial` に追加し、遠景の惑星等 (2.2節) が過度に反射で目立たないよう個別調整余地を残す。

```ts
// src/render/SceneSetup.ts 追加スケッチ
const pmrem = new PMREMGenerator(renderer);
scene.environment = pmrem.fromScene(new RoomEnvironment(), 0.04).texture;
pmrem.dispose();
```

**タスク分解**:
1. `PMREMGenerator`+`RoomEnvironment`の導入コードを`setupScene()`に追加(起動時1回のみ、ループ内では再生成しない)。
2. `MeshFactory.ts` の `body`/`accent` マテリアルに `envMapIntensity`(既定0.6〜1.0程度)を明示的に追加し調整余地を作る。
3. ビジュアルレビューで金属機体の反射強度を`envMapIntensity`で微調整。

**受け入れ基準**:
- 機体の金属パネルに周囲環境を反映した明暗のグラデーションが生じ、単調な`flatShading`の平面感が緩和される。
- 環境マップ生成は起動時1回のみで、フレームごとの追加コストがない。

**リスク**: 低コストな施策だが、`RoomEnvironment`は「部屋」を模したIBLのため、宇宙空間の機体に対しては反射が「室内的」に見えすぎる可能性がある。ビジュアルレビューで違和感が強ければ、自作の簡易グラデーション`CubeTexture`(空色→暗黒のシンプルな2色グラデーション)への差し替えを検討する代替案を残す。

## 3. Phase 2: 戦闘の手触り (ジュース)

### 3.0 性能予算 (Phase 2 全体に適用)

- **フレーム予算**: 60fps (`physicsConfig.ts:4` の `fixedDt=1/60` と描画を同期させる方針を崩さない)。VFX起因のフレームドロップは許容しない。
- **パーティクル上限**: 同時アクティブパーティクル総数 2000〜3000個を目安の上限とし、`VfxManager.activeCount()` で計測(1.2節)。上限超過時は最古のエフェクトから間引く(プールのリングバッファ的運用)。
- **GC回避**: `new Mesh`/`new Material`/`new Vector3` をエフェクト発生ごとに行わない。爆発・トレイル・マズルフラッシュは全て起動時に確保した固定長プール(`InstancedMesh`の`count`可変利用、または`Points`の`BufferAttribute`書き換え)を再利用する。`ExplosionSystem.ts:40`(`new MeshBasicMaterial`を`spawn()`ごとに生成)は本フェーズで置き換える対象。
- **描画コール削減**: デブリ・火花はエフェクトごとに個別`Mesh`を生成せず`InstancedMesh`でまとめ、ドローコールを1エフェクト種別あたり1〜数回に抑える。
- **モバイルGPU配慮**: パーティクルジオメトリは低ポリ(`SphereGeometry`は現状`(1,12,12)`程度、`ExplosionSystem.ts:21`と同水準を上限に)。`ShaderMaterial`を使う場合はフラグメント負荷の高いノイズ計算をパーティクルに持たせない(テクスチャベースのスプライトで代替)。モバイル検出時にパーティクル上限・Bloom解像度・SMAA→FXAAを自動的にダウングレードする設定分岐を`VfxManager`または`SceneSetup`に持たせる。

### 3.1 多層パーティクル爆発

**目的**: 現状の「発光球1個が膨張して消える」(`ExplosionSystem.ts:74-77`)を、閃光+衝撃波リング+デブリ+煙+火花の多層構成に再設計し、撃墜の満足感を作る。

**現状**: `ExplosionSystem.spawn()` (`ExplosionSystem.ts:39-52`) は`size/color/ttl`3パラメータで単一`Mesh`を`push`するのみ。`destroyed`イベントで`size=60, color=0xffaa33, ttl=1.1`、`hit`イベントで`size=10, color=0x66ccff, ttl=0.35` (`ExplosionSystem.ts:35-36`) の2パターンしかない。

**技術方針**:
- `ExplosionSystem`を「1発の爆発=複数レイヤーの同時spawn」を行うディレクタに再設計する。既存の`events.on("destroyed", ...)`/`events.on("hit", ...)`購読構造(`ExplosionSystem.ts:35-36`)は維持し、`spawn()`内部を多層化する。
- レイヤー構成(`destroyed`時、`hit`時は閃光+火花のみの軽量版):
  1. **閃光 (flash)**: 既存の`SphereGeometry`拡大フェード(`ExplosionSystem.ts:47-51`相当)を維持、ただし`ttl`を短く(0.15秒程度)して「一瞬の光」に絞る。
  2. **衝撃波リング (shockwave)**: `RingGeometry`または`TorusGeometry`を`AdditiveBlending`で外側に拡大しながらフェード(`MeshFactory.ts:166`の`createNavMarker`のトーラス表現パターンを流用可能)。
  3. **デブリ (debris)**: `InstancedMesh`(`BoxGeometry`or`TetrahedronGeometry`低ポリ、5〜10個)を爆発中心からランダム方向に飛散させ、簡易的な重力/減速を`update()`内で積分。撃破された機体のスケール感に応じ個数を調整。
  4. **煙 (smoke)**: 半透明`Sprite`または小さい`Points`群を上昇・拡散させながらフェード、`ttl`を長め(1.5〜2秒)に。
  5. **火花 (sparks)**: `Points`(`AdditiveBlending`, 小サイズ多数)を短命(0.3〜0.5秒)で放射状に飛ばす。`hit`イベント(被弾、まだ撃墜ではない)ではこの火花+軽い閃光のみを発生させ、`destroyed`との差別化を明確にする。
- `VfxManager`(1.2節)にこれら5種を個別プール(`register("explosion.flash", ...)`等)として登録し、`ExplosionSystem`自体はイベント購読とプール呼び出しの薄いオーケストレーション層に縮小する。マテリアルは種別ごとに共有インスタンスを使い、`opacity`のみパーティクルごとに`InstancedMesh`の場合は頂点カラー/`InstancedBufferAttribute`で個体差を出す(`new Material`per-spawnをやめる、`ExplosionSystem.ts:40`からの変更点)。

```ts
// src/game/systems/ExplosionSystem.ts 再設計スケッチ
interface ExplosionLayers {
  flash: boolean; shockwave: boolean; debris: number; smoke: number; sparks: number;
}
const DESTROYED_LAYERS: ExplosionLayers = { flash: true, shockwave: true, debris: 8, smoke: 6, sparks: 24 };
const HIT_LAYERS: ExplosionLayers = { flash: true, shockwave: false, debris: 0, smoke: 0, sparks: 6 };

private spawnLayered(position: Vector3, layers: ExplosionLayers, scale: number): void {
  if (layers.flash) this.vfx.spawn("explosion.flash", { position, scale });
  if (layers.shockwave) this.vfx.spawn("explosion.shockwave", { position, scale });
  if (layers.debris > 0) this.vfx.spawn("explosion.debris", { position, count: layers.debris, scale });
  if (layers.smoke > 0) this.vfx.spawn("explosion.smoke", { position, count: layers.smoke });
  if (layers.sparks > 0) this.vfx.spawn("explosion.sparks", { position, count: layers.sparks });
}
```

**タスク分解**:
1. `VfxManager`に5プール(flash/shockwave/debris/smoke/sparks)を登録する初期化コードを追加(`bootstrap.ts`または`SceneSetup.ts`起動時)。
2. `ExplosionSystem`を`VfxManager`呼び出し型に再設計、`destroyed`=フルレイヤー、`hit`=軽量レイヤーに分岐。
3. デブリの簡易物理(重力+空気抵抗的減速)を`update()`内でプール側に実装。
4. 撃墜機体の`faction`/サイズに応じて`scale`パラメータを`destroyed`イベント(`faction`は既存フィールド、`ExplosionSystem.ts:35`)から決定するロジック追加(大型機はより激しい爆発)。
5. 性能計測(3.0節)に合わせ、同時多発撃墜時(範囲攻撃・友軍全滅シーン等)のパーティクル総数が上限を超えないようテスト。

**受け入れ基準**:
- 撃墜時に「閃光→衝撃波→デブリ飛散→煙→火花」が視認でき、単一球体膨張だった旧実装より明確に情報量が増える。
- 被弾(`hit`)と撃墜(`destroyed`)が視覚的に明確に区別できる(被弾は軽い火花、撃墜は多層フル演出)。
- 同時に5機撃墜されても60fpsを維持する(3.0節の上限内で動作)。

**リスク**: レイヤー数が多いほど1爆発あたりのドローコール/パーティクル数が増える。`InstancedMesh`化(デブリ)と`Points`化(煙/火花)を徹底し、`Mesh`個別生成を避けることが性能予算達成の前提。

### 3.2 マズルフラッシュ / エンジン・ABプルーム / 弾・ミサイルトレイル

**目的**: 発射・航行の瞬間的な視覚フィードバックを強化し、既存の単調な発光球(`MeshFactory.ts:83-94`のエンジングロー、`:100-111`の弾メッシュ)に動きと余韻を加える。

**現状**: マズルフラッシュは存在しない(`WeaponSystem.ts:78-82`の`weaponFired`emit時に視覚効果の生成コードは無く、`AudioManager.ts:16`が音のみ再生)。エンジングローは`Mesh`固定形状+`scale.set(1,1,1.6)`(`MeshFactory.ts:92`)の静的な楕円発光のみでプルームの噴射感がない。弾は`createProjectileMesh`(`MeshFactory.ts:100-111`)で`scale.set(1.2,1.2,6)`の伸びた発光球のみ、軌跡(トレイル)は残らない。

**技術方針**:
- **マズルフラッシュ**: `weaponFired`イベント拡張(1.2節の`muzzlePosition`/`direction`)を購読する新規`MuzzleFlashSystem`(または`VfxManager`直結)を追加。`kind==="gun"`時は小型`Sprite`(`AdditiveBlending`, 数フレームで消える, ttl<0.08秒)を`muzzlePosition`に生成。`kind==="missile"`時はより大きく短い閃光。既存`createProjectileMesh`(`MeshFactory.ts:100`)のマテリアルパターン(`AdditiveBlending`+`depthWrite:false`)を流用。
- **エンジン/ABプルーム**: `MeshFactory.ts:90`の`glow`(`engineGlow`という`name`で識別済み、`MeshFactory.ts:93`)を起点に、新規`EnginePlumeSystem`(可変レート)が各機体の`engineGlow`ノードを毎フレーム走査し、`ThrusterInput.afterburner`(オーディオ仕様書`05_技術仕様_オーディオ.md`で言及される既存コンポーネント)がtrueの間、`scale.z`を脈動させる+背後に`Points`ベースの噴射パーティクル(短命、機体後方に放出されてすぐ消える)を追加。既存の`glow`メッシュ自体の改修は不要(名前で検索して追加ノードをぶら下げるだけ)。
- **弾トレイル**: `createProjectileMesh`(`MeshFactory.ts:100`)で生成される弾に対し、`InstancedMesh`ベースの「軌跡リボン」(`CylinderGeometry`を弾の移動履歴に沿って引き伸ばす、または単純に発光度が減衰する複数の残像`Sprite`を弾の後方に一定間隔でスポーン)を追加。曳光弾特有の「線が伸びる」感を出す。
- **ミサイルトレイル**: `createMissileMesh`(`MeshFactory.ts:176-191`)の`flame`(`MeshFactory.ts:184-189`)を起点に、煙を引く`Points`列を`InstancedMesh`かパーティクルプールで実装(弾トレイルより長寿命・煙質)。


1. `WeaponSystem.ts:78-82,102-106`の`emit`に`muzzlePosition`(既存`muzzleWorld`変数を再利用)と`direction`(既存`fwd`変数)を追加。
2. `MuzzleFlashSystem`新規作成、`VfxManager`にマズルフラッシュ用プール登録。
3. `EnginePlumeSystem`新規作成、`obj.getObjectByName("engineGlow")`(three.js標準API)で既存グローノードを取得し脈動+噴射パーティクルを追加。
4. 弾トレイル: `spawnProjectile`呼び出し箇所(`WeaponSystem.ts:66-75`)にトレイル生成フックを追加。
5. ミサイルトレイル: `spawnMissile`呼び出し箇所(`WeaponSystem.ts:94`)に同様のフック追加。

**受け入れ基準**:
- 発砲の瞬間、マズル位置(機体中心でなく実際のハードポイント)に短い光が視認できる。
- アフターバーナー使用中、エンジン後方の発光が単調な静止楕円でなく脈動・噴射感を持つ。
- 弾/ミサイルが移動軌跡を引き、発射地点から着弾地点までの弾道が視覚的に追いやすくなる。
- いずれも60fps予算内(3.0節)で、同時発射数が多い乱戦でもフレーム落ちしない(トレイルは寿命を短く+プール共有で制御)。

**リスク**: マズルフラッシュ・トレイルは発射頻度が高い(連射武器)ため、最もパーティクル数を消費しやすい機能。プールサイズの上限設計(3.0節)をこの機能から優先的に検証する。

### 3.3 カメラシェイク / FOVキック / ヒットストップ

**目的**: 単純`lerp`追従(`CameraRig.ts:42`)+固定`lookAt`(`CameraRig.ts:47`)のみの現状カメラに、被弾・撃墜・発射の衝撃を伝える演出を追加する。

**現状**: `CameraRig.update()` (`CameraRig.ts:28-48`) は`stiffness`(既定6)による`position.lerp`と`camera.lookAt(lookTarget)`のみ。外部からカメラの一時的な状態(シェイク量、FOV変化)を注入する仕組みが無い。`Game.frame()` (`Game.ts:45-70`) はヒットストップ(時間スケール制御)の概念自体を持たず、`frameTime`は`performance.now()`差分をそのまま使う(`Game.ts:48`)。

**技術方針**:
- **カメラシェイク**: `CameraRig`に`shakeTrauma: number`(0..1の減衰する外傷値、Trauma-based shake の定石パターン)を追加。`EventBus`の新規`cameraShake`イベント(1.2節)を購読して`shakeTrauma`を加算、`update()`内で`Math.pow(shakeTrauma, 2)`に応じたパーリンノイズ的な位置/回転オフセットを`camera.position`/`camera.rotation`に加算してから`lookAt`する(`lookAt`の後にシェイクを乗せると視線がブレて見えるため、オフセットは`lookAt`前に位置へ加算する順序が重要)。
- **FOVキック**: `camera.fov`(`SceneSetup.ts:25`の初期値70)を、被弾/撃墜/AB使用時に一瞬引き上げてから`updateProjectionMatrix()`で戻す。`CameraRig`に`fovKick(amount, duration)`メソッドを追加し、内部で減衰するオフセットを`update()`ごとに`camera.fov`に加算・`updateProjectionMatrix()`。
- **ヒットストップ**: `Game.ts:48`の`frameTime`計算後、`hitStopTimer > 0`の間は`frameTime`を大幅に縮小(例: `frameTime *= 0.05`)して物理・アニメーションをほぼ停止させつつ描画は継続する「一瞬の時間停止」を実現。`Game`クラスに`triggerHitStop(durationMs)`APIを追加し、強撃墜(`destroyed`)時などに`EventBus`経由で呼ぶ。既存の固定タイムステップ構造(`Game.ts:51-59`)を壊さないよう、ヒットストップは`accumulator`に加算する`frameTime`のみをスケールし、`PHYSICS.fixedDt`自体は変更しない。

```ts
// src/render/CameraRig.ts 拡張スケッチ
export class CameraRig implements System {
  private shakeTrauma = 0;
  private fovOffset = 0;

  addShake(intensity: number): void { this.shakeTrauma = Math.min(1, this.shakeTrauma + intensity); }
  kickFov(amount: number): void { this.fovOffset += amount; }

  update(world: World, dt: number): void {
    // ...既存のdesiredPos/lerp処理 (CameraRig.ts:34-43)...
    this.shakeTrauma = Math.max(0, this.shakeTrauma - dt * 2.5); // 減衰
    const shakeAmt = this.shakeTrauma ** 2;
    this.camera.position.x += (Math.random() - 0.5) * shakeAmt * 1.5;
    this.camera.position.y += (Math.random() - 0.5) * shakeAmt * 1.5;
    // ...既存のlookAt (CameraRig.ts:46-47)...
    this.fovOffset *= Math.max(0, 1 - dt * 6);
    this.camera.fov = 70 + this.fovOffset;
    this.camera.updateProjectionMatrix();
  }
}
```

```ts
// src/game/Game.ts:48 付近 拡張スケッチ
private hitStopMs = 0;
triggerHitStop(ms: number): void { this.hitStopMs = Math.max(this.hitStopMs, ms); }
// frame() 内、frameTime算出直後:
let frameTime = Math.min((nowMs - this.lastMs) / 1000, PHYSICS.maxFrameTime);
if (this.hitStopMs > 0) { frameTime *= 0.05; this.hitStopMs -= nowMs - this.lastMs; }
```

**タスク分解**:
1. `CameraRig`に`addShake()`/`kickFov()`メソッドと内部減衰ロジックを追加。
2. `EventBus`に`cameraShake`イベント(1.2節)を追加、`hit`/`destroyed`購読側(新規`CameraFeedbackSystem`または既存`ExplosionSystem`拡張)から`cameraShake`をemitする(自機が関与する場合のみ発火し、無関係な遠方の爆発では震わせない=関与判定が必要)。
3. `Game`クラスに`triggerHitStop()`を追加し、`frame()`内の`frameTime`計算にヒットストップ処理を挿入。
4. 自機撃墜/大型武器発射など「強い瞬間」にのみヒットストップを発火するトリガー箇所を選定(`DamageSystem.ts:64`の`destroyed`emit箇所付近、対象がプレイヤー機かどうかの判定を追加)。
5. FOVキックはAB使用開始/被弾/撃墜で強度を変え、`ThrusterInput.afterburner`変化検知(既存コンポーネント)と連携。

**受け入れ基準**:
- 被弾時にカメラが短く震え、方向感覚を失わない範囲(振幅を抑えた減衰)で衝撃が伝わる。
- 撃墜の瞬間、FOVが一瞬広がり速度感が強調される。
- 自機撃墜等の「決定的瞬間」でわずかな時間停止が感じられ、かつ物理シミュレーションの固定ステップ精度(`PHYSICS.fixedDt`)自体は変更されない。
- シェイクは`lookAt`前の位置オフセットとして実装され、視線のブレが不自然にならない。

**リスク**: シェイク・ヒットストップの過剰使用は乗り物酔い/ゲーム性阻害のリスクがあるため、`shakeTrauma`の最大振幅とヒットストップの最大時間に明確な上限を設け、設定でOFFにできる余地(アクセシビリティ)を将来的に残す。

### 3.4 ヒットマーカー / キルフィード / 被弾ビネット (HUD)

**目的**: DOM/CSSベースのHUD(`HudView.ts`)に、命中/撃墜/被弾の即時フィードバックをテキスト+視覚効果で追加する。

**現状**: `HudView.ts`は`speedEl`/`statusEl`/`weaponEl`/`objectiveEl`等の恒常表示要素のみ(`HudView.ts:66-133`のコンストラクタ)。命中/撃墜時の一時的なポップアップ要素は無い。`hud.css`は`.hud-messages`(`hud.css:167-177`, ミッションメッセージ用、中央上部)のみで、ヒットマーカーやキルフィード専用のクラスは無い。`hud`全体は`pointer-events:none`(`hud.css:4`)、`z-index:10`(`hud.css:9`)。

**技術方針**:
- **ヒットマーカー**: `hit`イベント(発射元がプレイヤーの場合のみ)を購読し、画面中央に短時間(0.15秒程度)表示する「×」または「+」型マーカーを`reticle`(`HudView.ts:93`, `hud.css:57-73`)に重ねてフラッシュさせる。既存`hud-reticle`の疑似要素パターン(`hud.css:66-73`の`::before`/`::after`)に倣い、新規`.hud-hitmarker`クラスをCSSアニメーション(`opacity`+`scale`の一瞬のパルス、`transition`または`@keyframes`)で実装。DOM要素は`HudView`コンストラクタで生成し`update()`外で`flashHitMarker()`のような専用メソッドから`classList`トグルで発火する(既存の`update(d: HudData)`一括更新パターンとは別に、イベント駆動の一時表示は専用メソッドが自然)。
- **キルフィード**: 撃墜(`destroyed`)イベントを購読し、画面右上あたりに「あなたは XXX を撃破」のようなテキスト行を追加、数秒後にフェードアウトして消える。既存`.hud-messages`(`hud.css:167`)のミッションメッセージとは別領域に`.hud-killfeed`を新設し、複数行のキュー(最大3〜5件、古いものは自動で消える)として実装。`renderMessages()` (`HudView.ts:203-205`) の`innerHTML`一括再構築パターンと同様、`killFeedEntries: {text, age}[]`を内部状態として持ち`update()`のたびに寿命判定してHTML再構築する。
- **被弾ビネット**: 自機が`hit`/`shieldHit`(1.2節新規イベント)を受けた際、画面全体に赤い縁取り(ビネット)を一瞬強めて減衰させる。実装は`.hud`直下に`.hud-damage-vignette`(`position:absolute; inset:0; pointer-events:none;`)を追加し、`box-shadow: inset 0 0 120px rgba(255,60,60,alpha)`のような効果を`opacity`アニメーションで発火。2.1節の常時ビネット(`ShaderPass`、環境ムード用)とは別レイヤーで、こちらはDOM側の一時的な被弾フィードバック専用。
- いずれも`HudView`に`EventBus`購読を追加する必要があるため、`HudView`のコンストラクタ引数に`events: EventBus`を追加する変更が必要(現状`HudView`は`HudData`を`update()`で受け取るだけの受動的ビューであり、`EventBus`への直接依存は無い、`HudView.ts:85`)。この設計変更の是非は呼び出し側(`HudSystem`相当、`bootstrap.ts`でのHUD生成箇所)との責務分離を確認して決定する。

```ts
// src/hud/HudView.ts 拡張スケッチ (コンストラクタで購読)
constructor(container: HTMLElement, events: EventBus, isPlayer: (id: EntityId) => boolean) {
  // ...既存要素生成 (HudView.ts:86-131)...
  events.on("hit", (e) => { if (isPlayer(e.source)) this.flashHitMarker(); if (isPlayer(e.target)) this.flashDamageVignette(0.4); });
  events.on("destroyed", (e) => { if (/* 発射元がプレイヤー */) this.pushKillFeed(`撃破: ${/* 敵名 */}`); });
}
private flashHitMarker(): void { this.hitMarkerEl.classList.remove("flash"); void this.hitMarkerEl.offsetWidth; this.hitMarkerEl.classList.add("flash"); }
```

**タスク分解**:
1. `HudView`コンストラクタに`EventBus`(と発射元/対象がプレイヤーかどうかの判定関数)を渡す設計変更。呼び出し側(`bootstrap.ts`のHUD生成箇所)の修正含む。
2. `hud.css`に`.hud-hitmarker`/`.hud-killfeed`/`.hud-damage-vignette`クラスと`@keyframes`アニメーションを追加。
3. `HudView`に`flashHitMarker()`/`pushKillFeed(text)`/`flashDamageVignette(intensity)`メソッドを追加。
4. キルフィードのキュー管理(`killFeedEntries`配列、`update()`内で寿命超過分を除去して再描画)。
5. 「発射元/対象がプレイヤーか」の判定ロジックをどこに置くか決定(`HudView`に`isPlayer`関数を注入する形が既存の`getPlayer`パターン(`bootstrap.ts:68`の`CameraRig`引数と同型)と一貫性がある)。

**受け入れ基準**:
- プレイヤーが命中弾を当てた瞬間、レティクル付近にヒットマーカーが一瞬表示される。
- プレイヤーが撃墜した瞬間、画面右上にキルフィードが追加され数秒でフェードアウトする(複数撃墜が短時間に発生してもキューが破綻しない)。
- プレイヤー自機が被弾した瞬間、画面縁が赤く一瞬強調され、ダメージが多いほど強く表示される。
- `pointer-events:none`(`hud.css:4`)の既存方針を崩さず、これらの新規要素も操作を妨げない。

**リスク**: `HudView`に`EventBus`依存を追加することで、現状の「`update(d: HudData)`一括受動更新」という単純な設計が「イベント駆動の副作用も持つ」ハイブリッドになる。責務が肥大化しすぎる場合は、ヒットマーカー/キルフィード/ビネット専用の小さな`HudFeedbackView`クラスに分離し、`HudView`とは別にDOMツリーを持たせる代替案も検討する。
