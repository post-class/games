# 06 技術仕様: コンテンツとAI (Phase 4 / 5 / 6)

本紙は【Phase 4 実アセット】【Phase 5 戦術と敵の多様性】【Phase 6 生きたキャンペーン】の技術仕様。
ロードマップ全体の位置づけ・優先順位は [`03_ロードマップ.md`](./03_ロードマップ.md) を、物語・セーブ・僚機名簿の恒久データは [`07_技術仕様_メタ進行と物語.md`](./07_技術仕様_メタ進行と物語.md) を参照。

このゲームの最大の資産は **データ駆動設計** である。機体は `SHIP_DEFS`（`src/game/ships/shipDefinitions.ts`）、ミッションは `MISSIONS`（`src/game/mission/missions.ts`）にデータとして定義され、「増やせば増える」。本フェーズ群の要諦は、**個々のコンテンツを作る前に“型（スキーマ）を拡張”して、量産の土台を先に作る**ことにある。

---

## 0. 現状棚卸し

- 機体は4種（`shipDefinitions.ts`: rapier / dralthi / transport / gratha）。すべて `visual.kind:"primitive"`（`shipDefinitions.ts:46` 等）でプリミティブ描画。`ShipDefinition`（`src/game/ships/ShipDefinition.ts:46-59`）は既に `hardpoints: Vec3Tuple[]`（`ShipDefinition.ts:54`）を持つが、武装は単一砲＋ミサイル数のみの `ShipWeaponDef`（`ShipDefinition.ts:33-43`）で、**武器の種類・スロットの概念がない**。
- 武装は実質2種。`WeaponSystem`（`src/game/systems/WeaponSystem.ts:41-48`）が「エネルギー砲」と「ミサイル」を発射するだけ。ミサイルは `MissileSystem`（`src/game/systems/MissileSystem.ts:29-45`）で単純に `turnRate` で目標へ旋回する誘導のみ。**シーカー種別・対抗手段（チャフ等）が存在しない**。ミサイル威力は砲の3.5倍固定（`WeaponSystem.ts:99`）。
- AIは5状態FSM（`Idle/Pursue/Attack/Evade/Form`、`src/game/components/AIController.ts:4`）。遷移は純関数 `evaluateTransition`（`src/game/systems/AISystem.ts:317-339`）に集約され、距離・照準ドット・タイマーのみで分岐。戦術は「偏差射撃＋ジョスト（突き抜け離脱）」の1種（`AISystem.ts:257-313`）、回避は**乱数方向**（`AISystem.ts:233`）。索敵は最至近1体（`AISystem.ts:188-209`）。
- ミッションは3種（`MISSIONS`: patrol / escort / strike）。目標型は4種 `destroyAll/protect/reachNav/survive`（`src/game/mission/MissionDefinition.ts:45-49`）、ウェーブトリガは3種 `start/afterWave/time`（`MissionDefinition.ts:12-15`）。キャンペーンは直線で、失敗は常に `retry`（`missions.ts:141-148`、`CampaignNode` は `success`/`failure` のみ `missions.ts:136-139`）。

**方針:** 上記スキーマ（`ShipDefinition` / `MissionDefinition` / `CampaignNode` / `AIController`）を後方互換に拡張し、既存4機体・3ミッションが動いたまま新要素を“載せる”。

## 1. Phase 4 — 実アセット

### 1.1 GLTF機体パイプライン

**目的:** プリミティブ機体を実3Dモデルへ。第一印象の「安っぽさ」を消す（[`01`](./01_現状診断.md) 2.1）。

**現状:** 差し替え口は既に存在する。`createShipMesh`（`src/render/MeshFactory.ts:29-33`）は `visual.kind:"gltf"` を見て `createGltfShipMesh`（`MeshFactory.ts:114-143`）へ分岐し、非同期ロード＋キャッシュ＋失敗時フォールバック（`MeshFactory.ts:146-153`）まで実装済み。**データを差し替えるだけで移行できる。**

**技術方針:**
- `ShipDefinition.visual` を `kind:"gltf"` にし `gltf.url` を与える（`ShipDefinition.ts:13`）。プリミティブ定義は残し、モデル未用意の機体はプリミティブのまま運用（段階移行）。
- 素材は **CC0 中心**（Kenney "Space Kit"、Quaternius "Ultimate Spaceships" 等）。ライセンス表記を `public/credits.txt` に集約。
- 最適化: `gltf-transform` で Draco 圧縮・テクスチャリサイズ・重複マージ。1機あたり目標 <300KB。読み込み中はフォールバック形状が出るので**待たせない**。
- 機体の向き規約（機首 +z、`MeshFactory.ts:23`）に合わせ、モデルの軸ズレは読み込み後に `model.rotation` で正規化。`gltf` 定義に任意の `rotationOffset?: Vec3Tuple` / `scale?: number` を追加できるようにする。
- エンジングロー位置（現状 `MeshFactory.ts:90` の固定球）はモデル内の名前付きノード（例 `engine_L`）を探して差し替え、無ければ従来ロジック。

```ts
// VisualDefinition.gltf の拡張（ShipDefinition.ts:13 を置換）
gltf?: {
  url: string;
  scale?: number;               // モデル寸法の正規化
  rotationOffset?: Vec3Tuple;   // 軸ズレ補正（機首を+zへ）
  engineNodes?: string[];       // 噴射位置に使うノード名（P2トレイルの装着点）
};
```

**タスク分解:** ①`gltf` 拡張フィールド追加 → ②`MeshFactory` で正規化・エンジンノード検出 → ③rapier/dralthi をGLTF化して検証 → ④残り機体を順次 → ⑤クレジット整備。

**受け入れ基準:** `visual.kind:"gltf"` の機体が正しい向き・スケールで表示され、ロード失敗時はフォールバックで進行継続。60fps維持（[`08`](./08_マイルストーンと受け入れ基準.md)）。

**リスク:** モデルのポリ数過多でモバイル負荷 → LOD/デシメーション。軸・スケール規約の不統一 → `rotationOffset`/`scale` で吸収。

### 1.2 キャピタルシップと破壊可能サブシステム

**目的:** 戦場にスケール感と「山場」を与える。小型機のドッグファイトに、巨大艦・砲塔・弱点という別レイヤーを足す（柱1「映画のような宇宙」・柱3「生きた戦場」）。

**現状:** 最大の艦は `transport`（`shipDefinitions.ts:107-150`、radius 22）で、単一の `Health`（shield/armor/hull）を持つのみ。**砲塔も部位破壊もない。**

**技術方針:**
- キャピタルシップを **親エンティティ＋子サブシステム群**でモデル化。各サブシステム（砲塔・エンジン・シールド発生器・ブリッジ）を個別 `Health` を持つ子エンティティとし、ローカル座標にマウント。
- 新コンポーネント `Subsystem`（親参照・種別・破壊時効果）と `Turret`（索敵・旋回・発射）を追加。砲塔は既存の `WeaponSystem` 経路を流用（`ThrusterInput.firePrimary` 相当を砲塔用に発火）。
- `ShipDefinition` に任意の `subsystems?` を追加（無い機体は従来どおり単一Health）。

```ts
interface SubsystemDef {
  id: string;
  kind: "turret" | "engine" | "shieldGen" | "bridge" | "hangar";
  localPos: Vec3Tuple;
  radius: number;
  hullMax: number;
  /** 破壊時の効果: シールド発生器→本体シールド無効化、エンジン→機動停止 等 */
  onDestroyed?: "disableShield" | "disableEngine" | "disableWeapons";
  weapon?: string;   // kind:"turret" のとき参照する Weapon 定義ID（§2.1）
}
interface ShipDefinition {
  // ...既存 ...
  subsystems?: SubsystemDef[];
  isCapital?: boolean;   // レーダー表記・当たり判定・AI対象の扱いを変える
}
```

- 破壊時は `subsystemDestroyed` イベント（P0で追加）を発火し、演出（[`04`](./04_技術仕様_描画と手触り.md)）・音（[`05`](./05_技術仕様_オーディオ.md)）・目標達成（§3.1 `disable`）に接続。
- 巨大メッシュの当たり判定は「サブシステム球の集合＋本体OBB近似」。既存の線分-球スイープ衝突（`tests/collision.test.ts` で担保）を子球に対して回す。

**タスク分解:** ①`Subsystem`/`Turret` コンポーネント → ②`ShipFactory`（`src/game/ships/ShipFactory.ts`）でサブシステム子生成 → ③砲塔AI（索敵→旋回→偏差射撃、§2.5の一部流用）→ ④破壊連鎖と `onDestroyed` 効果 → ⑤1隻（Kilrathi 護衛空母想定）をデータ定義。

**受け入れ基準:** 砲塔を個別に破壊でき、シールド発生器破壊で本体シールドが落ちる。無力化目標（§3.1）と連動。

**リスク:** サブシステム数×衝突計算の負荷 → 近接時のみ子球判定を有効化。AI が巨大艦へ突入する事故 → キャピタル半径を考慮した離脱距離を持たせる。

### 1.3 情景（小惑星・ステーション）

**目的:** 空虚な宇宙に構造物を置き、戦術的遮蔽とスケールを与える。

**技術方針:** 静的エンティティ（`Transform`＋`Renderable`＋衝突用 `Health` 無効の障害物）として配置。小惑星帯は `InstancedMesh`（[`04`](./04_技術仕様_描画と手触り.md) の描画土台と共有）で数百個を1ドローコール。`MissionDefinition` に `scenery?: ScenerySpawn[]` を追加してデータ配置。

**受け入れ基準:** 小惑星帯ミッションで遮蔽物越しの戦闘が成立し、衝突（自機・弾）が機能。**リスク:** 障害物とAI経路の相互作用 → 当面AIは静的障害を単純回避（レイキャスト1本）に留める。

## 2. Phase 5 — 戦術と敵の多様性

### 2.1 武装システムの再設計（武器定義とスロット）

**目的:** 「単一砲＋ミサイル数」から、**複数の武器を装着・切替・グループ発射**できる汎用武装系へ。ロードアウト（§2.4）と多様な弾種（§2.2）の土台。

**現状:** `ShipWeaponDef`（`ShipDefinition.ts:33-43`）は砲パラメータ1組＋ミサイル数のみ。`WeaponSystem`（`WeaponSystem.ts:41-48`）は固定の砲/ミサイル分岐。`hardpoints`（`ShipDefinition.ts:54`）は既にあるが「砲口位置」としてしか使っていない（`WeaponSystem.ts:63-64`）。

**技術方針:**
- **武器をデータ定義 `WeaponDef` に外出し**し、機体は「ハードポイントにどの武器IDを載せるか」を持つ。後方互換のため旧 `weapon` は「既定ガン」を生成するアダプタとして残す。

```ts
type WeaponClass = "gun" | "missile";
type SeekerKind = "none" | "heat" | "aspect" | "torpedo"; // §2.2

interface WeaponDef {
  id: string;
  displayName: string;
  cls: WeaponClass;
  damage: number;
  projectileSpeed: number;   // gun: 弾速 / missile: 巡航速度
  range: number;
  fireInterval: number;
  energyPerShot?: number;    // gun
  ammoMax?: number;          // missile 系（機体積載）
  // missile 系のみ
  seeker?: SeekerKind;
  turnRate?: number;         // MissileSystem.ts:37 の m.turnRate に対応
  lockRequired?: boolean;
  projectileVisual: "tracer" | "bolt" | "missile" | "torpedo";
}

interface Hardpoint {
  localPos: Vec3Tuple;       // 既存 hardpoints を移行
  slot: "gun" | "missile";   // 装着可能クラス
  mountedWeaponId: string;   // ロードアウトで差し替え（§2.4）
}

// WeaponMount コンポーネント（実行時）を拡張
interface WeaponMount {
  hardpoints: Hardpoint[];
  groups: { primary: string[]; secondary: string[] }; // 同時発射する武器IDのグループ
  activeSecondary: number;   // 巡回選択される副兵装インデックス
  cooldowns: Map<string, number>;
  ammo: Map<string, number>;
  energy: number; energyMax: number; energyRegen: number;
}
```

- `WeaponSystem` は「入力（primary/secondary発射）→ グループ内の各武器を、個別クールダウン・弾種で発射」に一般化。砲は既存 `spawnProjectile`、ミサイルは `spawnMissile`（`src/game/weapons/projectileFactory.ts`）を弾種パラメータ付きで呼ぶ。
- 副兵装の**巡回選択**（例: `X` キーで heat→aspect→torpedo 切替）と**武装グループ**（複数砲を斉射/交互）を入力（`src/game/systems/InputSystem.ts`・`src/config/inputBindings.ts`）に追加。

**タスク分解:** ①`WeaponDef` テーブル＋既定ガンのアダプタ → ②`WeaponMount` 拡張と `WeaponSystem` 一般化 → ③副兵装切替の入力/HUD表示（`src/hud/HudView.ts`）→ ④既存4機体を新スキーマへ移行（挙動不変を確認）。

**受け入れ基準:** 既存の砲・ミサイルが新経路で挙動不変。複数の副兵装を切り替えて発射でき、HUDに選択中兵装と残弾が出る。

**リスク:** 大改修でリグレッション → 「既定ガンアダプタ」で旧データを温存し、テスト（`tests/`）を緑に保ちながら段階移行。

### 2.2 弾種の多様化（砲・ダムファイア・熱源追尾・魚雷）

**目的:** 状況に応じた武器選択の駆け引きを生む。

**現状:** ミサイルは常に単一の追尾ロジック（`MissileSystem.ts:29-40`）で、ロック時のみ誘導対象を付与（`WeaponSystem.ts:93-95`）。弾種の差は無い。

**技術方針（`seeker` で分岐）:**
- **dumbfire**（`seeker:"none"`）: 無誘導・高速・低コスト。近距離のとどめ用。`MissileSystem` は誘導分岐（`MissileSystem.ts:29`）をスキップし直進。
- **heat**（`seeker:"heat"`）: 後方＝敵エンジン排気に強い。ターゲットの**尾側**（相対方位）でロックが速く、正面からは入りにくい。アフターバーナー中の敵に吸われやすい（[`05`](./05_技術仕様_オーディオ.md) のAB状態と連動）。
- **aspect/image-lock**（`seeker:"aspect"`）: 全周ロック可だがロック時間が長い。`Targeting.lockProgress`（既存、`WeaponSystem.ts:95` 参照）のレート差で表現。
- **torpedo**（`seeker:"torpedo"`）: 対キャピタル用。低速・高耐久・要長時間ロック。小型機には当たらないが艦のサブシステム（§1.2）を割る。
- 弾種ごとに `turnRate`（`MissileSystem.ts:37`）・速度・寿命・当たり半径・見た目（`projectileVisual`）を変える。`MissileSystem` に「シーカー別のロック維持/見失い」を追加（§2.3の対抗手段が効く点）。

**タスク分解:** ①`Missile` コンポーネントに `seeker`/フレア感受性を追加 → ②`MissileSystem` にシーカー別誘導 → ③各弾種の `WeaponDef` 定義 → ④HUDのロック表示をシーカー別に。

**受け入れ基準:** 各シーカーが設計どおり挙動差を持ち（heatは尾側で強い等）、torpedoでキャピタルのサブシステムを破壊できる。

**リスク:** シーカー調整の沼 → まず heat/dumbfire の2種で体験を確立し、aspect/torpedoは段階追加。

### 2.3 対抗手段（チャフ／フレア／デコイ）とシーカー相互作用

**目的:** 「撃たれたら終わり」でない、ミサイル回避の読み合いを作る（柱2・柱5）。

**技術方針:**
- 消費型装備 `countermeasures`（機体積載数）を追加。`C` キーで射出。
- 射出すると短命の**デコイエンティティ**を後方に生成。`MissileSystem` の誘導判定に「近傍のデコイに一定確率で誘導が移る」を追加。**フレア**は `seeker:"heat"` に、**チャフ**は `seeker:"aspect"` に効きやすい、という相互作用テーブルを持つ。
- 敵AIもロックされたら（被ロック検知＝§2.5）確率でデコイを撒く＋回避機動へ。

```ts
interface CountermeasureDef { kind: "flare" | "chaff"; vsSeeker: Partial<Record<SeekerKind, number>>; }
// 例: flare = { vsSeeker: { heat: 0.7, aspect: 0.1 } }
```

**受け入れ基準:** 適切な対抗手段でミサイルを高確率で回避でき、種類不一致では効きが悪い。**リスク:** 常時デコイで無敵化 → 積載数・クールダウン・誘導移り確率で調整。

### 2.4 出撃前ロードアウト

**目的:** ミッション前に武装・対抗手段を選ぶ意思決定を与える（進行の一部、[`07`](./07_技術仕様_メタ進行と物語.md) のアンロックと接続）。

**技術方針:** ブリーフィング（`src/game/GameController.ts` の遷移）とデブリーフの間に**ロードアウト画面**を追加（`src/game/ui/MissionScreens.ts` のDOM/キーボードUIを流用）。選択結果を `WeaponMount.hardpoints[].mountedWeaponId` と対抗手段数に反映して `ShipFactory` へ渡す。アンロック済み武器のみ選択可（`SaveDataV2.unlocks`、[`07`](./07_技術仕様_メタ進行と物語.md)）。

**受け入れ基準:** ハードポイントに武器を割り当てて出撃でき、選択が実機体に反映。**リスク:** 選択肢過多で難解 → 既定ロードアウト＋「おまかせ」を用意。

### 2.5 AIの高度化（機動ライブラリ・効用ベース選択・士気・編隊・エース）

**目的:** 「乱数回避の1戦術」から、状況に応じて戦い方を変える手強い敵へ（柱2・柱3）。

**現状:** 遷移は `evaluateTransition`（`AISystem.ts:317-339`）、回避は乱数方向（`AISystem.ts:233`）、行動は `combatAction`（`AISystem.ts:257-313`）の1パターン。索敵は最至近1体（`AISystem.ts:188-209`）。

**技術方針:**
1. **機動ライブラリ**: 回避/攻撃機動をデータ化し、`Evade`/`Attack` 状態で状況に応じて選択。各機動は「目標角速度＋スロットル＋継続時間」を返す関数。

```ts
type Maneuver = "break" | "barrelRoll" | "splitS" | "jink" | "highYoYo" | "extend";
interface ManeuverPlan { setInput(ti: ThrusterInput, ctx: AIContext, t: number): boolean; } // 完了でtrue
// evadeDir 乱数（AISystem.ts:233）を、被弾方向・敵位置から選ぶ ManeuverPlan に置換
```

2. **効用ベースの戦術選択**: `evaluateTransition` を残しつつ、`Attack` 内の行動を「追尾／機動／離脱／ミサイル発射」の効用スコア（距離・被ロック・僚機状況・エネルギー・HP）で選ぶ薄い層を追加。既存FSMは骨格として維持。
3. **被ロック検知と反応**: `lockWarning`（P0イベント）を受け、確率でデコイ＋回避機動。
4. **士気・エジェクト**: `AIController` に `morale` を追加。HP低下・僚機全滅・被ロック継続で低下し、閾値超過で**離脱（extend）→ エジェクト**（脱出ポッド生成、`wingmanDown`/撃墜数の扱いは [`07`](./07_技術仕様_メタ進行と物語.md)）。
5. **編隊戦術**: 敵にもリーダー/ウィングマンのペア（既存 `formationSlot`、`AIController.ts:30` を敵にも活用）。1機が交戦、僚機が挟撃する「サンドイッチ」を、ターゲット共有で表現。
6. **名前付きエース**: `AIController` に `profile?`（aggression/精度/使用機動の重み/固有名）。エースは高精度・多彩な機動・高士気。撃墜すると [`07`](./07_技術仕様_メタ進行と物語.md) の戦績に刻まれる。

```ts
interface AIController {          // 既存(AIController.ts:13-31) を拡張
  // ...既存 role/state/target/aggression/evadeDir/detectRange/attackRange/order/formationSlot ...
  morale: number;                 // 0..1
  skill: number;                  // 命中/機動精度スケール
  maneuver: ManeuverPlan | null;  // 実行中の機動
  profile?: AceProfile;           // 名前付きエース
}
```

**タスク分解:** ①機動ライブラリ（まず break/jink/extend）→ ②`combatAction` に効用選択層 → ③被ロック反応 → ④morale/エジェクト → ⑤敵編隊の挟撃 → ⑥エースprofile。**各段は独立に足せる**（FSMは温存）。

**受け入れ基準:** 敵が状況で異なる回避を見せ、被ロックでデコイを撒き、劣勢で離脱/脱出する。エースは明確に強い。既存AIテスト（あれば）と `evaluateTransition` の純関数性を維持。

**リスク:** AIが賢すぎ/理不尽 → `skill`・難易度（`src/game/Settings.ts`）でスケール。計算負荷 → 機動選択は状態遷移時のみ評価しフレーム毎は再利用。

### 2.6 サブシステム照準

**目的:** キャピタル戦（§1.2）で「どこを狙うか」の意思決定を与える。

**技術方針:** `TargetingSystem`（`src/game/systems/TargetingSystem.ts`）に「ターゲット艦のサブシステム巡回選択」を追加（例 `U` キー）。選択中サブシステムをHUDに強調表示し、リード計算（`src/hud/ReticleCalc.ts`）を子エンティティ座標に向ける。**受け入れ基準:** 砲塔/シールド発生器を個別ロックして攻撃できる。

## 3. Phase 6 — 生きたキャンペーン

### 3.1 ミッション目標・トリガーの拡張

**目的:** 全滅/護衛/到達/生存の4型（`MissionDefinition.ts:45-49`）を超え、任務の多様性を出す。

**技術方針:** `ObjectiveDefinition` と `WaveTrigger` の判別共用体を後方互換に拡張。`MissionManager`（`src/game/mission/MissionManager.ts`）の目標評価に新型のハンドラを追加。

```ts
type ObjectiveDefinition =
  | { id; label; type: "destroyAll"; optional? }          // 既存
  | { id; label; type: "protect"; tag; optional? }         // 既存
  | { id; label; type: "reachNav"; nav; optional? }        // 既存
  | { id; label; type: "survive"; seconds; optional? }     // 既存
  | { id; label; type: "intercept"; tag; before: number }  // 新: 目標到達前に阻止
  | { id; label; type: "scan"; tag; duration: number }     // 新: 偵察（一定時間照準保持）
  | { id; label; type: "disable"; tag }                    // 新: 撃沈せず無力化（§1.2 サブシステム）
  | { id; label; type: "defend"; tag; seconds }            // 新: 拠点/ステーション防衛
  | { id; label; type: "escape"; nav };                    // 新: 離脱（ジャンプ点到達で撤退）

type WaveTrigger =
  | { type: "start" } | { type: "afterWave"; wave } | { type: "time"; seconds } // 既存
  | { type: "onObjective"; objective: string }   // 新: 目標達成/失敗で誘発
  | { type: "onSubsystem"; subsystem: string };   // 新: サブシステム破壊で誘発
```

- `scan` は既存のロック機構（`Targeting.lockProgress`）を流用。`disable` は §1.2 の `subsystemDestroyed` を集計。`escape` は `reachNav` の変種で「離脱＝成功」。
- 時間制限は既存 `survive` の逆（`before`）として `intercept` に内包。

**タスク分解:** ①型拡張 → ②`MissionManager` に新ハンドラ → ③各型のHUD目標表示（`src/game/systems/HudSystem.ts`）→ ④新型ごとにテスト（`tests/mission.test.ts` に倣う）→ ⑤サンプルミッション追加。

**受け入れ基準:** 新5型がデータ定義だけで成立し、達成/失敗判定と増援トリガが正しく発火。既存3ミッションは無改修で動く。

**リスク:** 判定漏れ → 目標型ごとにユニットテスト必須。

### 3.2 分岐キャンペーン（勝敗で物語が変わる）

**目的:** 「失敗＝retry」の直線（`missions.ts:141-148`）を脱し、勝敗・選択で戦線が変わる戦役へ（柱4）。

**技術方針:** `CampaignNode`（`missions.ts:136-139`）を拡張し、①勝敗で別ミッションへ分岐、②プレイヤーの選択（ブリーフィング室での進撃ルート選択、[`07`](./07_技術仕様_メタ進行と物語.md)）で分岐、③物語フラグ条件による分岐を可能にする。

```ts
interface CampaignNode {
  success: CampaignEdge;
  failure: CampaignEdge;   // "retry" | 別ミッション | 敗北ルートへ（nullで敗北END）
}
type CampaignEdge =
  | string                                   // 単一遷移（既存互換）
  | "retry" | null
  | { choices: { label: string; to: string; requires?: string }[] } // 選択分岐
  | { branch: { when: string; to: string }[]; default: string };    // フラグ分岐
```

- WCの肝である「**負けても続く**」を実装: 敗北時に `retry` ではなく「劣勢ルート」へ進める設計を可能にする（例: 護衛失敗 → 母艦後退ミッションへ）。
- 分岐状態・到達フラグは `SaveDataV2.campaignState`（[`07`](./07_技術仕様_メタ進行と物語.md)）に保存。既存の `SaveManager`（`src/game/SaveManager.ts`）は移行で対応。

**タスク分解:** ①`CampaignNode` 拡張とグラフ解決関数 → ②選択UI（ブリーフィング室、07と共同）→ ③敗北ルートのサンプル → ④分岐グラフのテスト（`tests/campaign.test.ts` を拡張）。

**受け入れ基準:** 勝敗・選択で異なるミッションへ遷移し、敗北しても物語が続く経路が動く。既存の直線キャンペーンは互換維持。

**リスク:** 分岐爆発で制作量増大 → まず「主線＋1本の敗北ルート＋1回の選択」に絞る。

### 3.3 僚機のミッション跨ぎ生存

**目的:** 「名前のある仲間」を作り、その生死を物語に持ち込む（柱3・柱4、詳細な名簿/パーマデスは [`07`](./07_技術仕様_メタ進行と物語.md)）。

**技術方針:** `AllySpawn`（`MissionDefinition.ts:26-34`）を「名簿ID参照」に拡張し、出撃メンバーは名簿（[`07`](./07_技術仕様_メタ進行と物語.md)）から生存者を割り当てる。ミッション中の戦死は `wingmanDown` イベント→名簿へ永続反映。ここでは「ミッション定義が固定の僚機ではなく名簿を参照する」という接続点のみ定義し、恒久データは07に委ねる。

```ts
interface AllySpawn {           // MissionDefinition.ts:26-34 を拡張
  // shipId は rosterId 指定時は名簿から解決
  rosterId?: string;            // 名簿の僚機を配置（07）
  shipId?: string;              // 従来: 匿名の中立/被護衛
  position: Vec3Tuple; facingYaw?: number; tag?: string; combatant: boolean;
}
```

**受け入れ基準:** 名簿の生存僚機が出撃に反映され、戦死が次ミッション以降に持ち越される。**リスク:** 07との責務境界 → 本紙は「参照の仕組み」、07が「名簿の実体・永続・演出」。

### 3.4 ペーシング設計

**目的:** 単調な「全滅×N」を避け、緊張と弛緩の波を作る。

**技術方針（設計指針）:** キャンペーンを「導入（哨戒/偵察）→ 上昇（護衛/要撃）→ 山場（キャピタル強襲/防衛）→ 転換（敗北ルート or 選択）→ クライマックス」の起伏で構成。1ミッション内も「静かな進出 → 遭遇 → 増援の山 → 離脱」の波を `onObjective`/`onSubsystem` トリガ（§3.1）で作る。ミッション長は5〜10分を目安。

**受け入れ基準:** 通しプレイで戦闘密度に起伏があり、同型ミッションが連続しない。**リスク:** 体感評価 → [`08`](./08_マイルストーンと受け入れ基準.md) の体感チェックで判定。

## 4. 実装順序の目安

1. **スキーマ拡張を先に**（`WeaponDef`/`Hardpoint`§2.1、`Subsystem`§1.2、`ObjectiveDefinition`/`CampaignNode`§3.1/§3.2）——既存4機体・3ミッションを緑に保ったまま。

3. **P5**: 武装再設計（§2.1）→ 弾種（§2.2）→ 対抗手段（§2.3）→ ロードアウト（§2.4）→ AI高度化（§2.5、段階投入）→ サブシステム照準（§2.6）。
4. **P6**: 新目標型（§3.1）→ 分岐（§3.2）→ 名簿接続（§3.3、07と）→ ペーシング（§3.4）。
