## [解決] 固有令のフラグが未適用（7 件）→ 実装済み（2026-08-09）
7 件すべて実装され、エリート 8 種の特性も入った。実装の要点:
- 令の名前で分岐せず、`orders.json` の `flags` の**値の型**で解釈する
  （数値=倍率/比率、真偽値=有無、オブジェクト=資源ごとの毎秒量）。
  二重旗のときは 倍率=両段の積 / 比率=両段の最大 / 真偽=論理和。
- 検算: 陣立て 3456→2943 / 火計 対建物のみ ×1.35 / 上陸 3456→4147 /
  交易 25 tick でちょうど 金 1.5 / 奉納 撃破コスト×0.5 が資源に /
  圧壊 騎兵→槍 895→1280（不利 0.7 を等倍に戻す）/ 方陣 士気 0 でも退却しないが HP 0 では死ぬ
- 解釈を決めた 2 件:
  - **上陸**: 「強襲」の内容が資料にないので、浅瀬・湿地に足を置いている間だけ
    (a) 低所→高所の 0.9 を等倍に戻す (b) 与ダメージ ×1.2。
    「岸へ攻め上がる不利を消す」のが上陸の意味だという読み。
  - **圧壊**: `03§7` の獣兵「槍兵に止められない突破力」に合わせ、
    相性倍率を**等倍に寄せる**（不利 0.7→1.0、受ける側の 1.5→1.0。有利は伸ばさない）。
    押し出しは戦象の特性 `knockback` が担うので令には持たせなかった。
- 残り 2 フラグ未適用: `formationKeep`（配置 = movement 担当）/
  `requiresWaterFront`（令を出す側の検査 = command / UI 担当）。
  「`orders.json` の flags は全部どこかで読まれている」テストに明示リストとして残してある。

## [保留] 市場の売却側の規定が資料にない

## [判断] 固有令の段の割り当て
- 手順書 T-M9-08 の指示による。`07§4` は「上段 = 移動・配置の方針（どこへ行くか・下がるか・
  何を建てるか）」「下段 = 攻撃目標の優先（何を狙うか・誰を護衛するか）」と定義し、
  固有令については **ローマ「方陣」= 上段 / マリ「交易」= 下段** のみを明記している。
  残る 6 件は「その令が何を変えるか」を上の定義に当てて決めた（`game/src/data/orders.json`）。
- 判定の指針: **隊形・前進量・移動範囲を変える令は上段、狙う対象の優先順位や撃破の扱いを
  変える令は下段**。これで上段どうし・下段どうしが排他になり、二重旗の組み合わせが意味を持つ。

| 令 | 文明 | 段 | 根拠 |
|---|---|---|---|
| 陣立て `jindate` | ヤマト | 上段 | 「防御隊形で被害を軽減」＝隊形（dense）と持ち場の重みを変える令。攻撃目標は既定のまま。配置の方針なので上段。下段の包囲・略奪と重ねて「固く構えて門を叩く」が成立する |
| 火計 `kakei` | 唐 | 下段 | 「建物へのダメージが増える」＝狙う対象を建物へ寄せる令。`targetPriority` の先頭を `building` にする。移動方針は変えない。包囲と同じ性質なので下段（＝包囲とは排他） |
| 上陸 `jouriku` | ヴァイキング | 上段 | 「水辺の戦域に強襲をかける」＝船から岸へ、どこへ行くかを決める令。前進の重みを最大にする移動の方針そのものなので上段 |
| 奉納 `hounou` | アステカ | 下段 | 「撃破数が資源に変わる」＝隊形も前進量も変えず、建物よりも生きた敵ユニットを撃破する方へ優先を寄せる令。攻撃目標の扱いを変えるので下段 |
| 圧壊 `assai` | ペルシア | 上段 | 「正面の敵陣を押し崩す」＝密集して直進する隊形＋前進最大の令。突撃の上位互換的な移動・配置の方針なので上段（＝突撃とは排他になるのが妥当） |
| 遊撃 `yugeki` | モンゴル | 上段 | 「戦域を跨いで移動し続ける」＝戦域の枠を越えて動き回るという移動の方針そのもの。上段にすることで下段（略奪など）と重ね、「動きながら村人を狙う」というモンゴルらしい運用が作れる |

- 結果の内訳: 固有令 8 件のうち **上段 5（陣立て・方陣・上陸・圧壊・遊撃）／下段 3（火計・交易・奉納）**。
  各令の `note` にも同じ根拠を `【段の判断】` 付きで残してある（テスト `data.orders.test.ts` で検証）。
- 記録日: 2026-08-09

## [解決] AI の内政が回っておらず、文明差が盤に出ていなかった
- 発見の経緯: T-M18-04（文明バランスの総当たり）で「8 文明の勝率が揃って 50.0%」という
  一見きれいな結果が出たが、内訳を見ると**文明ごとの兵が 1 体も出ていなかった**。
  勝率が揃っていたのは均衡ではなく「差が出る前に試合が終わっていた」ことの結果だった。
  **数字が目標に一致したときこそ中身を見る**必要があるという例。
- 実測（2 人戦・30 分・段階 3）で分かった不具合 4 件と、それぞれの直し方:

| # | 症状 | 原因 | 直し方 |
|---|---|---|---|
| 1 | 生産された村人が全員手空きで立ち続ける（30 分で `gather` が **1 回**） | `classifyVillagers` が新しい村人を全員「建設係」にし、建設係は借りられるまで何もしない。着工は 1 判断 1 棟なので余りが出続ける | 建設係を `villagerBuilderCount`（既定 2）人だけ残し、**それを超えた村人はその場で採集に送る** |
| 2 | 石材と金の採集量が 30 分で **0**（開始値のまま） | 採集先を「いちばん足りない資源」にしていた。食料と木材は入った瞬間に村人と家へ消えるので常に最下位になり、石材と金が永久に選ばれない | 割り当てを **`RESOURCE_IDS` の順番**に散らす（乱数を使わず通し番号で決める） |
| 3 | 村人が数体で止まる（人口の大半が兵） | 同じ食料を村人と兵が取り合い、`planMilitary` が勝っていた | **`villagerTarget` に達するまで兵を作らない**（敵が見えているときは例外） |
| 4 | 全コマンドの **96〜97%** が時代進化の空打ち | 資源を見ずに毎判断 `advanceAge` を出していた。`sim` は足りなければ黙って捨てるので気付けない | 費用が足りているときだけ出す。ついでに**研究より先に**出す（町の中心は研究中は進化できない） |

- 直した結果（15 分の実測。`tests/unit/ai.economy.test.ts` で固定）:
  `gather` が 1 → 16 件、石材が 100 → 430、人口が両者 23〜26（以前は片方が 0 になっていた）、
  時代進化の空打ちが消えた。
- 5 件目（最後の原因）: それでも age が 0 のままだったのは **同じ tick 内のコマンドの順序**だった。
  `Command` は並んだ順に同じ tick で実行されるので、村人の生産（食料 50）を先に出すと
  進化の費用が 1 体ぶん足りなくなって `startAgeAdvance` が false を返していた。
  費用は貯まっている・建物の条件も満たしている・研究も譲っている、のに進化しないという
  分かりにくい形で出る。**進化はその判断のいちばん最初に出し、出した判断では他に資源を使わない**
  ようにして解決（`planEconomy` が `advance` を push して即 return する）。
  - 教訓: `Command` の並び順は「決定論のため」だけでなく **AI の意図そのもの**でもある。
    同じ tick に「貯めたものを使う命令」と「別のことに使う命令」を並べてはいけない。
- 直った結果（実測・30 分）: **両プレイヤーが age 1（青銅の世）に到達**するようになった。
  代償として人口は 22 前後 → 12 前後に減る（貯めるあいだ村人生産を止めるぶん）。
  時代が進まないと文明ごとの兵種が 1 つも出ないので、この取引を採った。
- **T-M18-04（文明バランス）は再測定が必要**。以前の「8 文明が揃って 50.0%」は
  文明差が出る前に試合が終わっていた結果なので、この修正後の数字とは意味が違う。
  なお 30 分でも age 1 までなので、鉄器・帝国の世の兵を測るには
  さらに内政の速さ（採集人数の配分）を詰める必要がある。

  働かせていなかった**。
- 原因: 採集していたノードが枯れると `sim`（`economy.ts` の `seekSameResource`）が
  次のノードを探すが、見つからなければ `Idle` で止まる。`AiView` に
  「そのユニットが何をしているか」が無かったので、AI はそれに気付けなかった。
- 直し方: `AiView.OwnEntity` に `state`（`UnitState`）を足し、
  `planIdleVillagers` が遊休の村人を採集に戻す。**自分のユニットの状態なので透視ではない**
  （人間は `06§5` の `.`「遊休村人へジャンプ」で同じ情報を見ている）。
- 同じノードへ行く村人は**1 つの命令にまとめる**。人間なら「まとめて選んでクリック」＝
  1 操作なので、1 人ずつ出すと操作量（APM）を過大に数える
  （実測で APM が 86.5 まで上がり `01`「手数で勝たない」の 60 を超えた。まとめて 24.6 に戻った）。
- 結果: 採集が 6 人 → 16〜20 人、食料が 402 → 1,140〜3,206、**鉄器の世に初めて到達**。

## [判断] ローマが強い原因は戦闘ではなく内政だった（切り分けの記録）
- 2 シード 28 試合でローマ 78.6%。**まず「相性が効いていないのでは」を疑って実測した**

  作りたい兵の生産元（兵舎・射場・厩）を多く建てるので、

  「穴なし＝どこも突出していない」がそのまま出た形。釣り合わせるなら
  「万能の代償」を別の形で入れる必要があり、資料に根拠のある形を選ぶ判断が要る。
  **ここは次に持ち越す。**
- 教訓: 勝率が偏ったとき、**まず「どの仕組みで勝っているか」を切り分ける**。
  切り分けずに数値を動かすと、正しく動いている部分を壊す。

## [重大] AI が試合を決められない ―― `attackTarget` を一度も出していなかった
- 112 試合すべてが時間切れ判定で **`gameOver` 決着が 0 件**。切り分けの実測:
  ```
   5分 兵 0/0  建物 8/10  町中心HP 2400/2400 敵拠点まで  -/-  マス 戦域 0
  15分 兵 5/7  建物 17/18 町中心HP 2400/2400 敵拠点まで 67/50 マス 戦域 0

  ```
  **町の中心の HP が 30 分間 1 も減っていない。** 兵は敵拠点の 14〜18 マスまで
  近づくのに建物を攻撃しない。

  的を名指しできなかった。`id` を足した ―― **これはズルではない**。

  **見えている建物をクリックするのは人間にできる通常の操作**（`06§5`）。
- もう 1 つ判明: `pushDispatch` は「いちばん近い目標」に 1 度送って 15 マス手前で令に返すだけで、
  兵の視界は 4〜6 マスなので**敵拠点が `seenEnemies` に一度も現れない**。
  そのため「返されて手の空いた兵を敵の開始位置へ送り直す進軍」も必要だった

- 実装後の実測（同じ seed）: 敵拠点まで **0 マス（隣接）**、
  町の中心 HP **2400 → 2026**（30 分時点）、**tick 51137（約 34 分）で決着**。

## [見た目] タイトルとキャンペーンが「素のまま」だった
- タイトルは CSS 図形（黒い塊の島＋白い丸の太陽）だけで、
  紋章の枠は**ただの黒い四角**＝壊れて見えた（`05§2-1` の「無地」の実装だが伝わらない）。
- キャンペーンは `05§5` が「**羊皮紙の環海図**に、章のメダルが時代順に並びます」と
  定めているのに、地図が無く**暗いリスト**に見えていた（メダルの並びは実装済みだった）。
- 直した点:
  - 島と碑を絵にした。**空と海は CSS のまま**にして絵は島だけを透過で重ねる ――
    `05§2` の「時刻とともに空の色が変わる」演出を殺さないため。
    絵が読めなければ CSS 図形に戻る（絵が無い環境でも壊れない）。
  - 島の下端をぼかした（生成した岸はほぼ直線なので、そのままだと海に貼ってあるように見える）。
  - 水平線に霞の帯を入れた。**最初は海のちょうど上に置いたが、
    空の色の上に空の色を重ねるだけで 1 px も変わらなかった**ので、線をまたぐ位置に下げた。
  - 無地の紋章に碑の影を置いた（黒い四角をやめた）。
  - 環海図を章選択の背景に敷いた（暗幕を重ねて文字の可読性を保つ。画像が無ければ暗幕だけ）。
- 記録日: 2026-08-11
